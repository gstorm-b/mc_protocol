## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** the plain config struct with `validate(where)` and a JSON mapping
  that covers every `FrameConfig` and `SessionConfig` field.
- **Approach:**
  - `include/mc/device/serial_transport.h`: `SerialSettings` only (with the
    `QSerialPort` enums and old defaults, spec open question 1); the
    `SerialTransport` class arrives in T46 — declare nothing that is not
    implemented.
  - `include/mc/device/mc_device_config.h` + `src/device/mc_device_config.cpp`:
    `TransportKind`, `SubscriptionSpec`, `McDeviceConfig` as the sketch.
    JSON keys: every field of the **existing** `FrameConfig` and
    `SessionConfig` (read `include/mc/core/frame_config.h`, `session.h`) under
    the same name; enums as strings; `"maxGap": "auto"` or a number (as the
    spec's JSON shows); serial enums as the strings shown (`"Even"`, `"1"`,
    `"None"`, data bits as a number). `fromJson`: missing keys → defaults,
    unknown keys ignored, wrong type or invalid value →
    `{Config, InvalidConfig}` with its JSON path in `where`; `"schema"` must be
    1. `validate()`: the checks listed in the sketch, first failure wins, path
    in `where` (e.g. `subscriptions[2].device`). `session.log` ignored.
  - Tests: `tests/device/tst_config_json.cpp` (QtTest, label `device`) + qmake twin.
- **Files expected to change:** `include/mc/device/serial_transport.h`,
  `include/mc/device/mc_device_config.h`, `src/device/mc_device_config.cpp`,
  `src/CMakeLists.txt`, `mc_device.pri`, `tests/CMakeLists.txt`,
  `tests/device/tst_config_json.cpp`, `tests/qmake/*.pro`.
- **Acceptance criteria:**
  1. QDV-10: round trip `toJson` → `fromJson` is equal (field by field,
     non-default values in every field); missing keys → defaults; wrong type →
     error with the path; `schema: 2` → error.
  2. An invalid subscription reports `subscriptions[i].device` as its path;
     each `validate()` rule (host empty, port 0, portName empty for Serial,
     baud ≤ 0, invalid frame, invalid session) has a test naming its path.
  3. A test enumerates the fields of `FrameConfig` and `SessionConfig` keys in
     the produced JSON so a field without a key fails (list kept next to the
     test with a comment pointing at the headers).
- **Common to every Phase 5 task:** see T-035 "Common to every Phase 5 task"
  (binding here too).
- **Gate 1 approval:** 2026-09-30 — leader, under the owner's delegation
  extended to Phase 5 (`rules.md`). Gate 2: leader, one commit for the phase.

- Deviations from plan (+ reason):
  - **JSON spellings not fixed by the spec** (the spec shows only `frame`, `code`... in prose and one example): `frame.frame` is `"3E"|"1E"|"3C"|"1C"|"4E"|"4C"` (the example's "3E"); every other enum uses its enumerator name: `code` `Binary|Ascii`, `series` `QL|IqR`, `format` `Format1..Format5`, `targetFamily` `IqR_Q_L|QnA|A`, `commandSet` `ACPU|AnA`, `cycleMode` `FixedRate|FixedDelay`, `transport.kind` `Tcp|Serial`; serial `parity` `None|Even|Odd|Space|Mark`, `stopBits` `"1"|"1.5"|"2"`, `flowControl` `None|Hardware|Software`, `dataBits` a number 5..8 (as the example). The heartbeat device is its canonical text (`formatDevice`). Please confirm `format` as `"Format1"` rather than `"1"`.
  - **A missing `"schema"` counts as 1.** The spec says both "missing keys take the defaults" and "`schema` must be 1"; I read the second as the value, so `{}` is a valid default document (QDV-10 "missing keys -> defaults"). `schema: 2`, `0`, `"1"`, `1.5` fail with path `schema`.
  - **`fromJson` does not call `validate()`.** It checks JSON types, integer-ness, ranges of the C++ field type, enumerator names and the heartbeat device text; whether a subscription's device text parses or fits the frame is `validate()`'s job (a subscription's `device` stays a free string, as the data model has it). Reason: the round trip and "wrong type -> error with the path" stay independent of semantics, and QDV-16 wants the path of the subscription from validate.
  - **`validate()` returns the underlying error**, not always `{Config, InvalidConfig}`: frame/session/transport failures are `{Config, InvalidConfig}` with a static message; a subscription that does not parse or does not fit the frame is `InvalidDevice` (`subscriptions[i].device`), a zero count is `PointCount` (`subscriptions[i].count`), as `parseDevice`/`RangeSet::add`/`ReadPlan::build` report them. "Fits the frame" is `ReadPlan::build` of that one subscription with `session.plan` (the engine's own planning test). The spec says only "the first failure is returned".
  - **Path spellings in `where`:** `frame` (the core error names no field), `session.heartbeat.device` (the only thing `SessionConfig::validate` checks), `subscriptions[i].device|count`, `transport.tcp.host|port`, `transport.serial.portName|baudRate` (JSON-style, following the JSON shape). `where` is cleared on success.
  - **`maxGap`:** `"auto"` or a number 0..4294967294; the number 4294967295 (the `kAutoGap` sentinel) is rejected with path `session.maxGap`, since `"auto"` is its only spelling.
  - The size guard in CFG_01 (`sizeof(FrameConfig) == 40`, `sizeof(SessionConfig) == 56`, 64-bit only) is best effort: padding can hide a new `bool`. The key lists are the real guard. Sizes verified on MSVC and MinGW GCC 13 (both binaries pass CFG_01).

   connect timer (≈2 s); it still asserts only the spec's bound.
