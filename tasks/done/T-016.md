- Deviations from plan (+ reason):
  - **`BitLayout::PackedLsbFirst` has no CMD/CMDD vector of its own.** Every reference CMD/CMDD
    bit example describes individual point values (e.g. "M100 = 1,1,0,0,1,1,0,0"), which is
    `Request`'s own default layout, `BytePerPoint` — none uses `PackedLsbFirst`. The module spec's
    Payload contract and this task's own Plan text both name it as in scope, so it needed its own
    proof: `QNA-BITS-PACKED` in `test_commands.cpp`, hand-computed the same way DEV-07 was
    (T-015) — a 16-point packed write (`0x55 0x55` → alternating 1/0) checked against literal
    expected bytes for both codecs, and a 5-point packed read reusing CMDD-06's own wire bytes
    (`10 10 10`) checked against a hand-derived packed byte (`0x15`).
  - **`encodeBits<Codec>()`/`decodeBits<Codec>()` process `PackedLsbFirst` in chunks of up to 8
    points, on the stack, rather than through one intermediate `BytePerPoint` buffer sized to
    `count`.** `count` is a `Request::count` (`uint16_t`, up to 65535 in the type, though the
    frame family's own field maximum is narrower) — a buffer sized to the widest possible `count`
    is not a fixed size, and this is `core-*` code with a zero-allocation guarantee. Chunking by
    exactly 8 points keeps every chunk boundary nibble-aligned for `BinaryCodec` (a `Codec::
    putBits`/`getBits` call always treats index 0 as the high nibble of its first byte), needs
    only an 8-byte stack array regardless of `count`, and reuses `field_codec.h`'s existing
    `putBits`/`getBits` exactly as T-014 left them — no new field_codec.h primitive needed for
    this.
  - **`qnaResponseData<Codec>()` itself checks `in.size` against the expected wire size and
    returns `LengthMismatch`** (CMDD-17), rather than leaving that entirely to a later frame-layer
    check. The module spec's own test-level table lists CMDD-17 under "L3 Commands: response data
    decoding" (§9.5), not under the L4 frame tests, so the length check is this layer's job.
  - **`QNA-IQR` (iQ-R subcommand/device dispatch) has no CMD/CMDD vector either** — CMD-01..14 are
    all Q/L (spec §9's own Appendix A common-parameters table: "Subcommand | Q/L (unless iQ-R is
    stated)"); the reference's own iQ-R examples (`V-3E-B-11`/`12`) are full 3E frames belonging
    to a later (frame-facade) task. Proved directly instead, reusing T-015's already-verified
    D100 QnA Binary iQ-R device bytes.
  - **PRIM-04-style "field overflow" reasoning applies here too, unstated in cmd.vec/cmdd.vec**:
    `qnaRequestData`/`qnaResponseData` trust `validate()` (core-model) for point-count and
    device-number width the same way `field_codec.h` and `device_encode.cpp` already do (T-014/
    T-015's own notes); nothing new to add for this task.
