## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** the serial column of the Session's fault table: EOT, silence-based
  flush, first-byte and inter-character deadlines, read retries, never-retried
  writes, `maxConsecutiveLinkErrors`.
- **Approach:**
  - `src/core/session` (`session_rx.cpp`, `session.cpp` and what they need),
    exactly per `SPEC-core-session.md` "Faults, retries, EOT", the `Flushing`
    state row, the `SessionConfig` serial fields and the receive-buffer
    overflow row:
    - serial timeout or protocol error → `Send(EOT)` (F4: `EOT CR LF`) when
      `sendEotOnError`;
    - `Flushing` until `serialFlushMs` of silence (every byte restarts it; the
      whole window is capped at `effectiveTimeoutMs()`, and reaching the cap
      counts as one more consecutive link error);
    - then a **read** is resent up to `readRetries` times with identical
      bytes; a **write** fails with `Timeout` and is never resent;
    - `maxConsecutiveLinkErrors` → `LinkFault{Timeout or ProtocolError,
      reopenTransport=false}`; a PLC error resets the counter (SES-20);
    - serial deadlines: `effectiveTimeoutMs()` to the first byte, then
      `serialInterCharMs` after each byte (SES-27);
    - unsolicited serial bytes are discarded (SES-24).
    Ethernet behaviour is unchanged.
  - Tests use the 3C golden vectors directly, as the spec's testing strategy
    says (subscribe `D100×3` on 3C F1: request = `V-3C1-01`, reply
    `V-3C1-02`, a truncated copy, or a wrong-SUM copy); `readRetries = 2`

- Interpretations of the spec (each is a choice between readings; tell me if the leader reads one differently):
  1. **Order inside the fault:** the item stays in flight through the flush and is resolved when the flush ends
     (read: resent; poll chunk: `Failed`; ad-hoc write: `RequestDone{Timeout}`), as the table lists "EOT, flush, then
     resend/fail". So after a timeout the only output is `Send(EOT)`; the `RequestDone` / chunk `Failed` follows
     `serialFlushMs` (or the cap) later. `linkDown` during the flush therefore completes that item with `LinkDown`.
  2. **EOT on every serial link error, including the one that faults** (`Send(EOT)` then the completions, then
     `LinkFault`); no second EOT when the flush cap faults. Without `sendEotOnError` only the EOT is skipped, the
     flush still runs.
  3. **Flush cap:** counts as one consecutive link error but not in `SessionStats::timeouts`; if it reaches the
     limit, `LinkFault{Timeout}` and the in-flight item fails with the error of the attempt that began the flush
     (e.g. `SumCheck`), not with the cap's own `Timeout`. Silence is checked before the cap when both are due.
  4. `maxConsecutiveLinkErrors = 0` behaves like 1 (the first error faults); `SessionConfig::validate()` unchanged.
  5. `SessionStats`: `bytesSent` includes EOT bytes; `framesSent` and `CycleInfo::requests` count request frames
     only (resends included, the EOT is counted in `eotsSent`).
  6. At the end of a flush a pending read is resent at once, before any queued ad-hoc request (the resend is part of
     the same exchange); the ad-hoc queue is served by the `dispatch()` that follows.
  7. Deadlines are evaluated in `tick()` only, as on Ethernet (the contract is "call `tick` at `nextDeadline()`"); a
     `bytesIn` after the deadline but before the `tick` just moves the inter-character / silence deadline.
