## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** the `tools/hil_capture` program skeleton and its two inputs: the profile JSON (one
  PLC + transport + frame configuration, scratch area, limits) and the plan JSON (steps with
  device references), both loaded, validated and resolved.
- **Approach:**
  - Wiring (`SPEC-build-packaging.md` "Build options", "Who may link `mc::mock`", the test
    table): `MC_BUILD_TOOLS` already exists in the top `CMakeLists.txt`; add
    `add_subdirectory(tools)` under it, `tools/CMakeLists.txt`, target `hil_capture`
    (Qt 6 console, links `mc::device` and `mc::mock`). QtTest binary `mc_hil_tool_tests`
    (label `hil_tool`, through `mc_add_qt_test()`, built only with tests + mock + device +
    tools). The tool's logic lives in sources the test binary compiles too (a small internal
    library target or a shared source list — your choice, explain it).
  - `profile.h/.cpp`: the JSON of spec "Profile" (`schema`, `profile{id, plc, module,
    firmware, adapter, plcState, scratch[], deviceEnd{}, supports[], scanTimeDevice,
    specialBit, specialWord, families[]}`, `device` = an `McDeviceConfig` read with the
    library's existing JSON loader, unchanged). Scratch ranges and `deviceEnd` numbers are
    parsed in each device type's own radix (X/Y/B/W… hex, from the core device table).
  - `plan.h/.cpp`: the plan JSON. Step kinds `write`, `read`, `poll`, `mutate`, `raw`,
    `bench`; expectations `ok`, `ok + values`, `plcError`, `timeout`, `noResponse`,
    `notSent`, `record`; `readOnly` for frames the mock cannot decode. Device references:
    `D@s`, `D@s+10`, `M@s16`, `D@end`, `D@end+1`, literal `D100`, resolved against a
    profile. **Read `docs/hil/COMMAND-CATALOGUE.md` first:** the schema must be able to
    express every step of the catalogue (T-063 writes the four real plans in it); list any
    catalogue step it cannot express in Dev notes instead of dropping it. Document the
    schema in a short comment block at the top of `plan.h`.
  - Example profiles `tests/hil/profiles/*.example.json`, one per bench row of the spec's
    "Profiles on this bench" table (Q CPU 3E Binary, Q C24 3C F4, FX5U 3E ASCII, FX3 1E
    Binary, FX3 1C F1). Addresses are placeholders only: IP from TEST-NET-1 (`192.0.2.x`),
    COM names `COM1`. FX3 `specialBit`/`specialWord` = `M8000`/`D8000`. A short
    `tests/hil/profiles/README.md` says the addresses are placeholders, the FX3 special
    devices and every scratch area are unverified until the owner's Checkpoint F gate, and
    real profiles stay local (`.gitignore` already ignores `tests/hil/profiles/*.json`
    except `*.example.json`).
- **Leader decisions for Phase 7 (binding for T-056…T-064):**
  - **D1 — no library change.** Nothing under `include/mc/`, `src/` changes. The tool uses
    the public API only (the `McDevice` constructor that takes a `std::unique_ptr<Transport>`
    exists). If the tool seems to need a library change → stop and report (owner decision).
  - **D2 — unknown keys are errors.** Profile and plan loaders reject an unknown key, a
    missing required key, a bad radix and an unknown device type with the JSON path
    (e.g. `profile.scratch[2]`), so a typo can never silently drop a safety field.
  - **D3 — captures made against `virtual_plc`/`MockPlc` never go to
    `tests/vectors/captured/`** (that folder is hardware-only). Tests and manual runs write
    to a folder under `build/`; the tool takes an output-root option, default
    `tests/vectors/captured/`. Small committed fixtures for testing the replay checks may
    live in `tests/hil/fixtures/<id>/`, their `run.meta` operator note saying
    "virtual_plc fixture, not hardware".
  - **D4 — one confirmation prompt.** The pre-run summary lists PLC identity, transport,
    scratch area and every `readOnly` frame the gate could not decode; typing the profile id
    confirms all of it; `--yes` skips that prompt. No flag skips the safety gate's checks.
  - **D5 — no real PLC.** Every run in Phase 7 targets `examples/virtual_plc` (loopback TCP,
    or the virtual COM pair `COM54,COM55`). `docs/hil/BENCH.md` and `FINDINGS.md` are not
    regenerated from virtual_plc data.
- **Common to every Phase 7 task (T-056…T-064):**
  - `SPEC-hil-capture.md` is binding for the files it owns (`tools/hil_capture`,
    `tests/hil`, `tests/vectors/captured`, `docs/hil`); `SPEC-build-packaging.md` for the

  - Qt 6.2 API minimum in the tool; `mc_replay_tests` stays std-only (never Qt, network or

  - New sources in CMake and their qmake twin per the Definition of Done (a new test binary
    gets its `tests/qmake` `.pro`; BLD guards stay green). If a qmake twin of the tool or of
    `mc_hil_tool_tests` is impractical, say why in Dev notes and propose — the leader decides.
  - Test names start with the spec's test ID (HIL-xx, RPL-xx).
  - Builds always parallel; temp files in `build/_scratch-<task>/` or `temp-docs/`, never
    `%TEMP%`; serial tests hold `RESOURCE_LOCK mc_serial_pair` and use
    `MC_TEST_SERIAL_PAIR=COM54,COM55` (never COM50; never touch the serial driver).
  - Verification (MSVC daily loop, one PowerShell call):

    — MinGW, qmake, check scripts and coverage run at Checkpoint F.
  - Phase-level verification: no tester or reviewer per task, no commit per task; the

  - `tools/hil_capture/options.h/.cpp`, `tool.h/.cpp`, `main.cpp`: the command line (all options of the spec's usage block plus `--output-root`, D3), the exit codes, `runTool()` (for now: load, resolve, one summary line; gate, dry run and runner come in T-058/T-060). `main.cpp` is thin so tests can call `runTool` with their own streams.
  - `tools/hil_capture/hil_capture.pri`, `tools/qmake/hil_capture.pro`, `tools/qmake/tools.pro`, `mc_protocol.pro` (changed: `tools_qmake`): qmake twin of the tool.

  - `tests/hil/hil_tests_main.cpp`, `hil_suites.h`, `hil_test_support.h`, `tst_hil_profile.cpp`: one binary, one QtTest class per `tst_*.cpp`, run in turn by the main (`--suite NAME` selects one; the serial suite of T-060 will be run that way under its own ctest entry). The main is not called `main.cpp` on purpose: in the qmake build jom picked the tool's `main.cpp` for `main.obj` (same basename in two source directories) and the test binary ran the tool.

- Design notes:
  - Shared sources: a static library target (`mc_hil_tool`) that the program and the test binary both link, so the sources compile once and CMake needs no second list. qmake cannot link a CMake target, so its twin is a `.pri` of the same sources, included by both `.pro` files.
  - Profile rules beyond the spec text (each reported with its JSON path): `profile.id` must be folder-safe (it names the folder a re-run deletes); `deviceEnd` of a hexadecimal type must be a JSON string; a scratch range cannot end beyond a declared `deviceEnd`; `device.subscriptions` must be empty (subscriptions belong to poll steps); an enabled heartbeat in `device.session` must lie in scratch (it writes every round); `specialBit` must be a bit device and `specialWord` a word device; `families` is one of `qna-ethernet`, `a1e`, `qna-serial`, `a1c` (the spec only shows `qna-serial`). Required keys: schema, profile.{id,plc,scratch,deviceEnd,supports,specialBit,specialWord}, device; the rest is optional.
  - Plan schema (read the `plan.h` header comment): `then`, `readBack`, `foreach`, `requires`, `frameOverride` (with `"+N"` relative numbers), `scratchTooSmall: skip`, `mirrors` placeholders `{x}`/`{n}`, value generators, bit strings, `expect` objects (`values`, `bitsOn`, `valuesFrom`, `frames`), mutate edits (`setByte`, `setNibble`, `append`, `truncate`, `replaceSum`), raw `hex` (with `{EOT}`) or `requests`, poll `actions` (write, subscribe, unsubscribe, prompt) and `bitsAsWords`, bench `request`/`pollSet`.
- Catalogue expressibility check (acceptance criterion 4). Every step of `COMMAND-CATALOGUE.md` was walked through. Expressible: G0-01/02 (`metaKey` keeps the scan time word for run.meta), GV-01..05, G1-01..10 (`readBack`, value generators, limit counts with `scratchTooSmall: skip`, `valuesFrom` + `frames` for G1-04, `{"f64":..}`/`{"i32":..}` for G1-10), G2-01..10 (`then` for the multi-operation steps; one step per type with `requires` for G2-07), G3-01 (`bitsOn`), G3-03..05, G4-01/02 (`foreach: supports|other`), G4-03/04 (`frameOverride` `e1AliasLS`, `commandSet`), G5-01..06 (G5-05 with `bitsAsWords`; G5-06 through `requires: ["profile:<variant id>"]`), G6, G7-01..05 (`truncate`, `setByte`, `replaceSum`, `frameOverride` `stationNo: "+1"`, `raw` with `{EOT}`, `recover`), G8-Q1..Q5 and Q7 (a `mutate` without edits sends a count the library would split, e.g. 129 or 41), G9-05 (a `mutate` with `frameOverride` `series: IqR`), G9-06 (`raw` `requests`), GB-01..11. Exceptions and caveats for the leader:
  1. **G9-02, G9-03, G9-04 (raw random writes `1402`, 1E `04H/05H`, 1C `BT/WT`)** cannot be expressed so that the safety gate can verify them: `MockPlc` does not decode those commands, so the plan could only mark them `readOnly: true`, which would be false for a write. They need a gate-side decoder for those frames (new work, a spec change) or they stay out of the plans.
  2. **G9-01 (`0403` random read) and G9-07 (4E)** need device fields inside a raw frame that are scratch-relative (`D@s+10`, `M@s16`). `raw` takes a literal `hex` only (or `requests` the library can encode); nothing builds device bytes without the library's private headers (D1). G9-07 also needs a 4E header that `McProtocol` does not encode. Not expressible unless the plan uses literal, profile-specific frames or a device-field macro is added.
  3. **G3-02** ("compare with G2-08 bits"): a consistency check across two steps; expressible only as `record`.
  4. **G6 and G7-06**: the "Expect" column (no `valuesChanged` in round 1, one snapshot per type, ...) is not judged by the tool; the poll is recorded and RPL-04 replays it. G7-06 (pull the cable) is a poll with a `prompt` action; the tool prompts, it cannot know the cable is out.
  5. **G8-Q8** is "none on this bench": no step, or a step guarded by a condition that never holds.
  6. Variants by data code or family need suffixed ids because ids are unique within a plan: G7-02 (3E subheader `50H -> 51H`, and the 1E command code `-> 7FH`) has a Binary and an ASCII form; `GB-11` needs `messageWait` 0 and 3 (`GB-11-w0`, `GB-11-w3`); `foreach` expansions are named `G4-01-D`, `G4-01-W`, ... The T-063 test that matches catalogue ids to plan ids must treat `<id>-<suffix>` as the catalogue id.
- Decisions the leader should know (spec reading):
  - **Poll subscriptions and the gate.** The spec says poll steps must lie inside scratch; the catalogue's G6 subscribes `X0 x 32` (inputs are never in scratch) and HIL-02 wants an out-of-scratch subscription refused. Both hold with one extra key: a subscription is checked unless it says `"input": true`. A subscription cannot write, so `input` costs no safety. The writes of a poll (heartbeat, ad-hoc writes) are always checked. Implemented in T-058.
  - `scratchTooSmall: skip` is the mechanism for "a step whose count exceeds the scratch area is skipped, not shrunk"; without it the step is refused by the gate.
