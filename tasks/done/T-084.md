  The bench case: QSerialPort opens a Windows port with DTR off. The QJ71C24N's RS-232 channel uses DTR/DSR control, so it never answered. The owner worked around it in the field by calling `setDataTerminalReady(true)` after open.
- **Goal:** `SerialTransport` asserts DTR (and RTS when flow control is not hardware) right after the port opens, by default, with a per-setting way to keep each line off.
- **Approach:**
  1. **`include/mc/device/serial_transport.h`:** add `bool dataTerminalReady{true};` and `bool requestToSend{true};` to `SerialSettings`, with Doxygen. Update the `SerialTransport` class Doxygen.
  2. **`src/device/serial_transport.cpp`, `completeOpen()`:** after `m_port->open()` succeeds and before `m_state = Open` / `emit opened()`:
     - `setDataTerminalReady(true)` when `dataTerminalReady`;
     - `setRequestToSend(true)` when `requestToSend` and `flowControl != QSerialPort::HardwareControl`.
     - A false return is not fatal. Log one `Warn` line naming the line and `errorString()` through the device's log path. If the transport has no log access, report that in the Dev notes and leave the line unlogged; do not add a new API for it.
     - When a setting is false, leave that line untouched rather than actively setting it false. Say in the Dev notes if Qt's open state makes that matter.
     - Qt 5.15 and Qt 6 must both work. `setDataTerminalReady` and `setRequestToSend` exist in both.
  3. **JSON (`src/device/mc_device_config.cpp`):** keys `transport.serial.dataTerminalReady` and `transport.serial.requestToSend`. Both are bool; a missing key is `true`; a wrong type gives the usual error with its path. QDV-10 cases: round trip, defaults, wrong type.
  4. **GUI fields (`tools/mc_workbench/config_binding.cpp`):**
     - `transport/serial/dataTerminalReady`: Bool, "DTR on after open (most devices, e.g. a C24 with DTR/DSR control, need it)";
     - `transport/serial/requestToSend`: Bool, "RTS on after open (ignored with hardware flow control)".

     Enable both only for Serial, as the other serial fields are. GUI-06 must pass.
  5. **Tests:** QDV-20 in `tests/device/tst_serial.cpp`, exactly as the spec row says. Read the peer's `QSerialPort::pinoutSignals()` on the other end of `MC_TEST_SERIAL_PAIR`; com0com maps DTR to the peer's DSR and RTS to the peer's CTS. Run it with `MC_TEST_SERIAL_PAIR=COM54,COM55` (**never COM50/COM51**). It must `QSKIP` without the variable. QDV-14 stays unchanged and green.
  6. **No change** to `Transport`, `TcpTransport`, the Session, or the `hil_capture` tool. Profiles read `McDeviceConfig` JSON, so they get the keys for free; confirm that a profile without the keys loads with both `true`.

Measured: with the line left alone the peer saw DSR on after open for the dtr-false rows (Qt's Windows open leaves DTR asserted on this pair), so QDV-20 failed. RTS false is left untouched and CTS stays off (rts-false rows pass). The DTR call is therefore unconditional: `setDataTerminalReady(settings.dataTerminalReady)`. Header Doxygen says so.
  - No Warn log line: `Transport`/`SerialTransport` has no log path (only `McDevice` logs, no transport signal for it). Per Plan, the refusal is unlogged (return values dropped with `(void)`), documented in the class Doxygen. No new API added. The spec's "one Warn log line" is therefore not met; leader decides whether a later task adds a transport log signal.
  - QDV-20 HardwareControl row checks only DSR and `opened()`: with hardware flow the driver owns RTS (handshake), so CTS is not asserted either way. "No warning" cannot be tested (no log).
