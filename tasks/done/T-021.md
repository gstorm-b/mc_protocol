## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** The value store of subscribed points: `include/mc/core/value_store.h`
  (`PointState`, `Change`, `SegmentView`, `ValueStore`).
- **Approach:** as the module spec's `value_store.h`: per-type segments with
  contiguous value and state arrays; `apply()` decodes one chunk's normalized
  payload with silent baselines (decision S4) and reports changes into caller
  storage; `markFailed`, `markStale`, `resetBaselines`; `rebuild()` carries
  values and baselines over a re-plan; bulk reads in the normalized layout.
  `apply()` and `markFailed()` never allocate.
- **Files expected to change:** `include/mc/core/value_store.h`,
  `src/core/session/value_store.cpp`, `src/CMakeLists.txt`, `mc_core.pri`,
  `tests/CMakeLists.txt`, `tests/core/session/test_value_store.cpp`,
  `tests/core/session/test_alloc.cpp`.
- **Acceptance criteria:**
  1. STO-01…STO-04 pass, and PLN-10 (moved from T-020): a re-plan carries value
     and state for surviving points, new points are `NoValue`, dropped points

  2. `apply()` and `markFailed()` allocate nothing — checked with
     `tests/common/alloc_counter.h` in `test_alloc.cpp` (the one including TU

- Deviations from plan (+ reason):
  - **Touched `include/mc/core/poll_plan.h`**, not in this task's file list: added
    `friend class ValueStore;` to `RangeSet`, mirroring the existing `friend class ReadPlan;`.
    `ValueStore::rebuild(const RangeSet& subs)` (the spec's own signature — a public API I must
    not change) has no way to enumerate `subs`'s subscriptions otherwise: `RangeSet`'s only
    public surface is `add/remove/size/empty`, with no iteration method, exactly as `ReadPlan`
    needed the same access in T-020. One-line, additive, no existing behaviour changed.
  - **`markStale()`/`resetBaselines()` are O(P) (P = total subscribed points), not the spec
    sketch's stated O(1) ("epoch counter").** Worked through an epoch/generation-counter design
    in detail before writing any code: it makes `state()`/`word()`/`bit()` resolve the "real"
    state lazily against a generation stamp, which does give O(1) `markStale()`/
    `resetBaselines()` — but it is incompatible with `segment()`/`SegmentView::states`, which
    the spec's own sketch exposes as a **raw `const uint8_t*` into the store's own array**: any
    caller reading that pointer directly (bypassing `state()`) would see stale, unresolved bytes
    that an epoch scheme never corrects except lazily, on the next `state()`/`apply()` touch of
    that exact point. Since `SegmentView` is a spec-mandated part of the public API (used later
    by Session's own `Snapshot` output, per the module spec's non-Qt usage example:
    `onSnapshot(out.deviceType, s.values())`), I judged eager-and-correct more important than
    O(1), and implemented both as a straightforward loop over every currently subscribed point.
    `apply()`/`markFailed()` (the two functions this task's acceptance criteria actually require
    zero-allocation for) are unaffected — still O(n) in the chunk's own point count, still
    allocation-free either way. Documented in both functions' own `@par Complexity`. Flagging
    for the leader/owner: if O(1) genuinely matters here (e.g. for a PLC with very large
    subscriptions and frequent reconnects), fixing it would mean changing `segment()`'s contract
    (e.g. to a resolved copy instead of a raw pointer) — a bigger, riskier change I did not make
    unilaterally.
  - `words()`/`bits()` (bulk reads) require `[head, head + count)` to fall entirely inside one
    `ValueStore` segment; a range that happens to be subscribed via *two* segments separated by
    a gap fails with `NotSubscribed` even though every individual point in it is, in fact,
    subscribed. Not called out explicitly either way by the spec sketch's doc comment; this is
    the only sound reading given `ValueStore`'s segments are never adjacent-and-separate by
    construction (an adjacent/overlapping pair is always unioned into one segment by
    `rebuild()`), so this only ever rejects a range that genuinely spans a real gap.
