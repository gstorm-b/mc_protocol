## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** The byte-level building blocks every frame uses: hex ASCII,
  8-bit sum check, and the `AsciiCodec` / `BinaryCodec` field codecs.
- **Approach:** per the module spec's "Field codecs": hex ASCII encodes
  upper-case and accepts lower-case on decode; sum check is the 8-bit sum as
  two ASCII hex characters; the field codecs write and read u8/u16/u32,
  fixed fields, bits, words, sizes byte-wise (no `reinterpret_cast`), honour
  the §2.1.1 exceptions, and never allocate. Internal headers under
  `src/core/protocol/` (`mc::detail`), nothing public.
- **Files expected to change:** `src/core/protocol/hexascii.h`,
  `src/core/protocol/hexascii.cpp`, `src/core/protocol/sumcheck.h`,
  `src/core/protocol/sumcheck.cpp`, `src/core/protocol/field_codec.h`,
  `src/CMakeLists.txt`, `mc_core.pri`, `tests/CMakeLists.txt`,
  `tests/vectors/prim.vec`, `tests/core/protocol/test_primitives.cpp`.
- **Acceptance criteria:**
  1. PRIM-01…09 and PRIM-12…17 pass, driven by `prim.vec`; PRIM-10, 11, 18
     are transcribed and tagged `v2` (skipped).
  2. A non-hex character decodes to `InvalidCharacter`; a value that does not
     fit its field yields the error the module spec names for that field.
  3. VEC-02 covers `prim.vec`; `ctest -L "core_protocol|core_model|build"`
     green on MSVC.

## Dev notes  *(developer writes)*

- Files changed:
  - `src/core/protocol/hexascii.h` / `.cpp` (new) — `hexEncode`/`hexDecode` (spec §2.1): every
    byte to/from two ASCII hex characters, upper-case on encode, upper/lower accepted on decode;
    `hexEncodedSize()`. The shared primitive `field_codec.h`'s `AsciiCodec` builds on.
  - `src/core/protocol/sumcheck.h` / `.cpp` (new) — `sumcheck()` (raw 8-bit sum) and
    `sumcheckEncode()` (2 ASCII hex chars, spec §2.5/E6), built on `hexEncode`.
  - `src/core/protocol/field_codec.h` (new, header-only per the module spec's Project
    Structure) — `BinaryCodec` and `AsciiCodec`, identical static-method signatures: `u8Size`/
    `u16Size`/`u32Size`/`bitsSize`/`wordsSize`/`dwordsSize`, `putU8`/`getU8`/`putU16`/`getU16`/
    `putU32`/`getU32`, `putBits`/`getBits` (nibble-packed for Binary, `'0'`/`'1'` chars for
    Ascii), `putWords`/`getWords`/`putDwords`/`getDwords` (sequences, normalized 2-/4-byte LE
    value side). See "Deviations" for what `field_codec.h` deliberately does not yet have.
  - `tests/vectors/prim.vec` (new) — one record per PRIM-01, 02, 03, 05, 06, 07, 08, 09, 12
    (×2: even/odd count), 13, 14 (×2: valid/invalid), 16 (×2: Ascii/Binary where both apply),
    typed from spec §9.2's literal Input/Expected columns; `# bytes: N` from the byte count of
    each record's own hex line. PRIM-04, PRIM-15, PRIM-17 have no record — see "Deviations".
  - `tests/core/protocol/test_primitives.cpp` (new) — a `kind:`-dispatched reader for
    `prim.vec` (`encode`, `decode`, `decode-error`, `sumcheck`, `bits-encode`, `bits-decode`,
    `bits-decode-error`) plus two standalone `TEST_CASE`s for PRIM-04 and PRIM-17.
  - `src/CMakeLists.txt`, `mc_core.pri` — added the three new header/source pairs to `mc_core`'s
    source list and `HEADERS`/`SOURCES` in the same change (BLD-04).
  - `tests/CMakeLists.txt` — added `core/protocol/test_primitives.cpp` to `mc_core_protocol_tests`
    and gave that binary its own `PRIVATE` include path to `src/` (mirrors `mc_core_model_tests`'s
    LIM-03 include, T-006) so the test can reach `core/protocol/field_codec.h` etc.

- Deviations from plan (+ reason):
  - **PRIM-04 (field overflow) has no `prim.vec` record and adds no new production code.**
    Re-reading the module spec's own wording ("Value wider than the field → `Encode/PointCount`
    for point counts, `Encode/InvalidDevice` for device numbers") together with Open Question 3
    ("always run `validate()` inside `encode()`, debug and release") shows this check already
    lives entirely in core-model's `validate()`, run *before* any codec sees a value — by the
    time a `Request` reaches `field_codec.h`, its point count and device number already fit their
    native C++ type width, so `putU8`/`putU16`/`putU32` take exactly `uint8_t`/`uint16_t`/
    `uint32_t` (which makes 256/65536 structurally unrepresentable, not just rejected). The
    exhaustive per-family cases are already implemented and tested in Phase 1: search
    `tests/core/model/test_frame_config.cpp` ("validate() rule 4", "validate() rule 6") and
    `test_device.cpp`. Since `grep PRIM-04` found nothing anywhere before this task (unlike
    PRIM-15, see below), I added one `TEST_CASE("PRIM-04 ...")` in `test_primitives.cpp` that
    reproduces one point-count and one device-number case through `mc::validate()` directly —
    a real assertion, not a comment, so the ID is both traceable and checked from
    core-protocol's own test binary, without duplicating the check itself or touching
    `test_frame_config.cpp` (outside this task's file list).
  - **PRIM-15 (words → bits) has no record or test here.** It is already `mc::convert::
    wordsToBits()`, tested and cross-referenced as `"CNV-06 (PRIM-15)"` in
    `tests/core/model/test_convert.cpp:71` (Phase 1, already committed). Re-testing it here
    would be exactly the "no logic duplicated" the Definition of Done rules out.
  - **PRIM-17 (property round trip) has no `prim.vec` record.** The reference spec's own L1 test
    level lists "table-driven + property-based" as two distinct methods (§9.1); a randomized
    round trip has no fixed data to transcribe into a vector. Implemented as a seeded
    (`std::mt19937(0xA5A5A5A5)`) loop, 64 iterations per type/codec, covering u8/u16/u32/bits/
    words/dwords for both codecs — reproducible across runs, per this project's no-flaky-tests
    norm.
  - **`field_codec.h` does not yet have a "fixed" byte-string field or a "words"/"dwords"
    *decode-side error path from an actual caller*.** The module spec's Project Structure line
    for `field_codec.h` lists "fixed" among its jobs (spec E1, the 3E/4E subheaders); that has no
    caller until the frame-envelope task, and the spec's own Code Style example for
    `frame_3e.cpp` keeps *two* separate literals (`kSub3eReqBin`, `kSub3eReqAsc`) side by side,
    which shapes what a `putFixed()` should even take as parameters — guessing that shape now,
    untested, would be the dead code the Definition of Done rules out. Flagging this so whichever
    task first writes a frame envelope (3E facade) plans to *extend* `field_codec.h` rather than
    treating it as finished. `putWords`/`getWords`/`putDwords`/`getDwords` themselves ARE
    implemented (PRIM-17 needs them) and reuse `putU16`/`getU16`/`putU32`/`getU32` per word/dword
    (no duplicated hex logic).
  - **Every `get*` (decode) function has a documented precondition, not a runtime check, that
    its input already holds enough bytes/chars** (`@pre` in `field_codec.h`). The only real,
    tested failure modes at this layer are: an `Ascii` decode's invalid hex character/bit
    character (`Protocol/InvalidCharacter`), and a `put*` encode's output buffer being too small
    (`Encode/BufferTooSmall`, `ErrorCode::BufferTooSmall`'s own doc comment is specifically about
    output capacity). An input-too-short concern belongs to the frame/command layer's own length
    checks (spec §5.1 etc., not yet written) — reusing `BufferTooSmall` for that direction would
    misuse an Encode-category code for a decode-side concern.

- Env notes (new facts about the build environment, for build-env.md):
  - Generating a long, repetitive hex line (PRIM-09's 300× `FF`) by having the model transcribe
    terminal output by eye is unreliable — the visible output can be silently truncated with no
    ellipsis or other marker. Safer pattern used here: write the generated text to a file
    (`perl -e '...' > /tmp/x.txt`, since this machine has no Python — `build-env.md` already
    notes that) and splice that file's exact content into the target file with `awk`/`sed`,
    never by retyping what a terminal printed. Worth adding to `build-env.md` for the next
    long-vector transcription (4C/3C Format 5, CMD-11/CMD-35, etc. all have very long lines too).
