## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** the threading backbone of the spec's "Architecture": every device and mock on its own
  runner thread, the GUI thread never blocked, failures contained, clean shutdown.
- **Approach:** in `mc_workbench_core` (no widgets):
  - `RunnerThread` owning one `QThread`; the runner object is **created inside** the thread
    (`QThread::started`), so `McDevice` / `MockPlc` and their children are born there.
  - `DeviceRunner`: owns `McDevice` (+ the `RecordingTransport` of `mc_hil_tool`); commands via
    queued `invokeMethod` (connect, disconnect, setConfig, subscribe, unsubscribe, submit); results
    and events as queued signals carrying **value copies**; batching of values/frames/log lines at
    ≤ ~30 emits per second.
  - `MockRunner` (basic): `MockPlc` served over loopback TCP — its own serving code
    (`examples/virtual_plc` stays unchanged, owner decision); COM serving comes in T-070.
  - Containment: every runner slot catches exceptions, reports a tab error, stops that runner.
  - Shutdown: stop → bounded wait → report a stuck thread instead of blocking; objects deleted on
    their own thread.
- **Acceptance criteria:** GUI-01, GUI-03, GUI-04 of the spec pass on MSVC and MinGW; a test asserts
  `QObject::thread()` of the device and the mock is the runner thread, never the GUI thread.
- **Gate 1 approval:** 2026-10-03 — leader (Phase 8 delegation). Common rules: `T-067.md`.

- Deviations from plan (+ reason):
  - "submit" is not one generic command: the host offers `readWords`, `readBits`, `writeWords`, `writeBits` (McDevice's own convenience calls). `mc::Request` carries a `data` view (a pointer into caller memory), which breaks the value-copy rule; the four calls take value copies. A raw `submit` can be added when the console task needs it.
  - Extra, small: `DeviceRunner::setValuesSlotHook()` — a test seam that lets GUI-03 make a slot connected to a `McDevice` signal throw (an exception inside the event loop, not under a posted command). `RunnerBase::liveRunners()/foreignDeletes()` are the "debug assertion hooks" of GUI-04.
  - `setConfig` builds a new `McDevice` (the transport must be injected to be recorded, and `McDevice::setConfig` keeps an injected transport). Runtime subscriptions are dropped, as `McDevice::setConfig` drops them. Only while Disconnected, else the command is refused.
  - `stop()` blocks the GUI thread up to the bound (default 3000 ms), as the spec says ("waits up to a bounded time"); `requestStop()` + the `finished()` signal give a fully non-blocking way for the tab code of the later tasks.
- Known limits, for later tasks (not defects of this one):
  - `RecordingTransport` keeps every chunk in memory (its design, for the capture writer); the runner only forwards the new chunks. T-072 (back-pressure, GUI-05) must bound this, e.g. by rebuilding the device per connect or a ring option; I did not touch `tools/hil_capture`.
  - `MockRunner` serves one client at a time (a new connection replaces the old one) over one shared `MockPlc`; memory image edits are visible to the client. COM serving, fault injection beyond `mute`, the request log records and the memory editor are T-070. The runner clears the `MockPlc` request log at every emit and reports only totals.

- Notes for the tester:
  - Thread assertions: `ThreadReport` (from `requestThreadReport()`) carries `QObject::thread()` of the runner, `McDevice` and `RecordingTransport` (device runner) and of the `QTcpServer` plus the thread the `MockPlc` was created on (mock runner); the test compares all with the host's `QThread`. A second check runs a `post()`ed functor on the runner thread. `liveRunners()` and `foreignDeletes()` prove object counts and no cross-thread delete.
  - "GUI keeps processing events (measured)": a 10 ms `Ticker` on the GUI thread; its largest gap stays under 250 ms while a runner throws, fails to open (closed port, missing COM253, busy COM54) or sleeps 900 ms in a command. The busy-COM case skips without `MC_TEST_SERIAL_PAIR` (the other 13 still run); with it, the whole binary takes the `mc_serial_pair` lock.
  - The stuck-thread cases sleep inside a posted command (900 ms; 4.5 s for the abandon case, so the case takes about 5 s); they leave no thread behind: each ends with a join or with the abandoned thread finishing (`liveRunners` back to the baseline).
  - Timing thresholds are generous (250 ms gap, 3 s stop bound); the 10 repeated runs per kit were not flaky, but run it under extra load too if you want more confidence.
  - Mutation ideas that should fail a test: create the runner in the GUI thread (move the factory call out of `started`); drop `guarded()` in `RunnerThread::post` or in the `valuesChanged` slot; delete the runner from the GUI thread in `RunnerThread`; make `stop()` wait without bound.
  - Env notes for `build-env.md`: new qmake sources of `mc_workbench.pri` need `build/qmake-*/tools/qmake/Makefile.mc_workbench*` and `build/qmake-*/tests/qmake/Makefile.mc_workbench_tests*` deleted before the next build (same gotcha as T-067). QtTest macros (`QTRY_*`, `QVERIFY`) `return;` and cannot be used in a function that returns a value; `QTest::qWaitFor` is `[[nodiscard]]` (C4834 under `/WX`).
