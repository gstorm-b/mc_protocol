## Review verdict  *(reviewer writes — skipped only if Class says so)*

- Reviewer: batch reviewer P9-2, 2026-10-14 (fresh agent; severity HIGH = blocker, MEDIUM = should-fix and blocks under the batch rule, LOW = nit).
- Findings (severity · file:line · what/why):
  1. **MEDIUM** · `src/core/model/chunk.cpp:51-57` (guard) with `src/core/session/adhoc_queue.cpp:70-78,234,280` · the packed-split guard is incomplete: it covers `WriteBits` + `PackedLsbFirst` only, but an ad-hoc packed **ReadBits** that splits at a cap that is not a multiple of 8 is corrupted the same way. `byteOffsetFor()` places chunk k's payload at `pointsCompleted / 8` (`chunkPayloadDest()`), so with `maxReadBits = 100` chunk 2 lands at byte 12 although it starts at bit 100 (byte 12.5), and it overwrites bits 96..99 of chunk 1. I reproduced it in `.wt/wt4` against the built `mc_core.lib`: `AdHocQueue(3E Binary, maxReadBits = 100)`, `Request::readBits(M0, 250)` with `bitLayout = PackedLsbFirst`: chunks 100/100/50, destSize 13/13/7; byte 12 after the last chunk = chunk 2's byte (0x00), not chunk 1's 0x0F. `submit()` calls `chunkCount()` first, which passes because the guard looks at `WriteBits` only. Silent data corruption on a read, introduced by T-088 (before it every table limit was a multiple of 8). No table value and none of the suggested values (480/480/1792/1792, 32/10/256/160) hits it; a user-set odd cap does. Fix options: (a) extend the guard to `ReadBits` + `PackedLsbFirst` (`Op::ReadBits` or `isBitOp()`), same `PointCount` error, plus a CHK-10 subcase and a SES-11 ad-hoc packed-read case with cap 100; or (b) round the effective bit cap down to a multiple of 8 for the two bit operations (always safe: a cap is an upper bound), but then `maxPoints()` is no longer exactly `min(table, cap)` as LIM-03 reads, a cap below 8 must not become 0, and the spec paragraph needs the rule.
