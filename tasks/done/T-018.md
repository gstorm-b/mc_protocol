- Deviations from plan (+ reason):
  - **"The runner reports them as skipped" (4E, acceptance criterion 1) is a real `TEST_CASE`
    that asserts every A.3/A.4 record is tagged `v2` and prints one `MESSAGE` per record**, not
    doctest's whole-`TEST_CASE`-level `doctest::skip()` decorator. 4E vectors are individual
    records inside a `.vec` file, not their own `TEST_CASE`s, so there is no per-vector "skip"
    concept in doctest to attach to; `MESSAGE` (unlike `INFO`, which only shows on failure)
    prints unconditionally, so a test run's own log is the human/CI-visible "report". The
    assertion on the `v2` tag is the real, falsifiable check: it would fail if a 4E record were
    ever left untagged (and so silently fed through some future frame_4e.cpp by mistake) or
    quietly dropped from the file.
  - **`3E-08a`..`3E-13a`'s ASCII forms needed their own derivation, not a mechanical doubling of
    the Binary ones** (the module's own vectors don't scale 1:1 in length between codecs once a
    literal field, like the subheader, is involved) — see "Commands run" for the one real
    transcription bug this caught (and how) in `3E-12a`/`3E-13a`.
  - **STR-02 "with 3E and with 1E" is done with 3E only.** 1E has no code yet (a later task); the
    acceptance criterion itself only requires 3E's own vectors for this task.

- Commands run / outcomes:
  - Derived every one of `3e_ascii.vec`'s six `*a` records the same way as T-017's Binary ones
    (spec §9.6's own recipe: modify or freshly build the ASCII equivalent), but generated each
    one's hex line from its text with a `perl -e 'unpack("H*", ...)'` one-liner rather than typing
    hex by hand, and cross-checked lengths against the Binary originals before trusting them.
  - `. scripts/vsdev.ps1; cmake --build build/cmake-debug` then running the binary directly
    caught two real bugs in my own hand-derivation, both in `3E-12a`/`3E-13a` (the two "route
    override" request vectors): I had transposed the `io` field's digits in an early draft of
    `3E-09a` (caught before it ever reached the vector file, by re-deriving with the same `perl`
    one-liner rather than trusting a manual re-check) and, more seriously, *omitted the
    monitoring-timer field entirely* while hand-writing `3E-12a`/`3E-13a`'s ASCII text, and got
    the request-data-length field wrong to match (`"1800"` instead of `"0018"`) — the actual
    `McProtocol::encode()` output was 42 bytes against my typed 38, caught immediately by
    `CHECK(sizeResult.value() == v.bytes.size())` failing with `42 == 38`. Regenerated both from
    the correct field list (subheader+network+pc+io+station+length+**timer**+request data) with
    the same `perl` one-liner, re-verified the hex-vs-text pairing, rebuilt — matched.
  - `ctest --test-dir build/cmake-debug -L "core_protocol|core_model|build" --output-on-failure`
    — 5/5 green (`BLD-08.version_agrees`, `core_model.mc_core_model_tests`,
    `core_protocol.mc_core_protocol_tests`, `BLD-04.pri_sync`, `BLD-05.include_hygiene`).
  - `mc_core_protocol_tests.exe` run directly: 27 test cases (19 from T-013..17 + this task's
    STR-01/02/04, the 4E-skip case, and ALC-01's two `TEST_CASE`s), 3679 assertions, all passing.
    STR-01 caught one real bug of its own along the way (see below) before the final green run.
  - STR-01's byte-at-a-time loop caught a genuine bug in *this task's own test code*, not a
    vector: my first `test_parser_stream.cpp` draft built every response vector's matching
    `Request` as a plain `ReadWords`/`ReadBits`, forgetting that `V-3E-B-06`/`V-3E-A-06` (and
    their `3E-*` siblings) are *write* responses — `REQUIRE(finalStatus == ParseStatus::Done)`
    failed (`Failed` instead) exactly on `V-3E-B-06` with a length mismatch, since a write
    response's expected wire size (0 bytes of data) does not match what a `ReadWords` context
    expects (6 bytes for count 3). Fixed by having the helper build the right op (a write needs
    no real write payload to reconstruct correctly for *parsing* purposes — confirmed against
    `command_qna.h`'s own contract, which never reads `Request::data` on the decode side).
