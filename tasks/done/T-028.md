  - **`cmake/mc_coverage_report.cmake` touched, though not in the Plan's Files list — a real,

    `src/core/session`'s own coverage, not new code from this task:** `src/core/session/
    read_plan.cpp` first reported `0/0 (100.00%)` — silently passing, but obviously wrong for a

    CMake represents a list as one semicolon-joined string, and the script populated its
    per-line list straight from each `.gcov` line's own text — which, being a source file's own
    annotated code, is full of literal `;` characters. `file(STRINGS)` does not escape those
    before joining, so an unescaped `;` inside one line's own text can make CMake's list
    re-parsing merge that line together with whichever lines follow, corrupting `list(LENGTH)` and
    `foreach()` for the rest of the file. Confirmed empirically (bisection on `read_plan.cpp.gcov`,
    a from-scratch reproduction with the exact same nested working directory the script itself
    uses, and a minimal 2-line repro): `file(STRINGS)` returned 26 "lines" for a 267-line file,
    with most of the file merged into one giant list item. **This is not unique to
    `read_plan.cpp`** — it is a property of `file(STRINGS)` + any line containing an unescaped
    `;`, which is every non-trivial C++ source's own gcov output; `core-model`/`core-protocol`'s

## Engine fit note (developer, acceptance criterion 4 — honest account, not softened)

Written from having implemented every one of T-020 through T-027 personally, plus this
checkpoint's own coverage work; file:line references are to the working tree as of this task.

**Where sans-I/O was a natural fit, not a compromise:**

- The whole engine is `TimeMs now` passed explicitly into every input method, with no clock read,
  thread, or blocking call anywhere in `src/core/session/*.cpp` (mechanically checked every task:
  `grep -nE "<chrono>|<thread>|std::chrono|sleep|<fstream>"` — always clean). This is not a
  constraint fought against; it is *why* every one of SES-01 through SES-27's several hundred
  assertions runs deterministically, with no timing flakiness, no real sockets, no threads, in a
  fraction of a second (the whole `mc_core_session_tests` binary — 63 cases, 9418 assertions —
  runs in well under a second on this machine). SES-23 ("byte-at-a-time delivery yields the same
  outputs as delivered whole", `tests/core/session/test_session_poll.cpp`) is the clearest single
  example: that property is close to untestable *reliably* against a real socket, and is a
  five-minute test here, because "a byte arrived" is just a function call with a `ByteView` of
  length 1.
- `dispatch()`'s own structure (`src/core/session/session.cpp:378-`) maps almost line-for-line
  onto the spec's own numbered "Dispatch" steps (ad-hoc priority, current round's next chunk,
  start a new round, heartbeat first, else idle) — reading the function next to the spec section
  is close to reading the same document twice. The heartbeat (T-026) and ad-hoc (T-025) priority
  rules slotted into this same one function without restructuring it, because "one step, maybe
  send something, return" was already the shape before either feature existed.
- Every state transition is a plain field write the *next* call observes — no callbacks, no
  promises, no continuation objects. `faultLink()` (`session.cpp:293-`) — arguably the most
  complex single function in the engine (three-way branch on what was in flight, plus draining
  every other queued ad-hoc job, plus tearing down and emitting `LinkFault`) — is still a flat,
  top-to-bottom function with no hidden control flow, entirely because there is no async
  machinery to route *through*.

**Where it forced real contortions — the honest part:**

- **The "zero-copy `Output`" design's own recurring lifetime hazard needed *three* independent
  mechanisms kept consistent with each other, and a phase-review blocker proved they had not
  been.** `Output`'s `chunks`/`changes`/`payload` fields (`include/mc/core/session.h`) are raw
  pointers into `Session`'s own `m_plan`/`m_changeBuf`/ad-hoc arena, not owned copies — a
  deliberate choice for zero allocation. This means a `Snapshot`/`ValuesChanged`/`RequestDone`
  still sitting undrained in the output ring becomes a dangling read (or a leaked reservation) the
  moment the buffer it points into is reused. Three separate places in the code each have to honor
  that same contract for it to actually hold:
  1. **`m_pendingPlanRefs`** (`session.h:492`, incremented at `session_rx.cpp:220,267`, read at
     the deferral guard `session.cpp:409`) — T-024's own fix for `Snapshot`/`ValuesChanged`
     pointing into `m_plan`/`m_changeBuf`, found as a real bug after T-023 shipped without
     noticing it (a round ending with a re-plan pending, immediately followed by the next round
     starting in the *same* input call).
  2. **`AdHocQueue::confirmDrained()`** (called only from `Session::nextOutput()` when popping a
     `RequestDone` — `adhoc_queue.h`'s own class doc, `session.cpp`'s `nextOutput()`) — T-025's own
     independent rediscovery of the *identical* hazard for the ad-hoc arena, needing its own
     bespoke mechanism because nothing generalized #1 to a second buffer.
  3. **`Session::checkDrained()`**, the drain-contract's own discard path (`session.cpp`,
     T-026) — a *third* place an `Output` leaves the ring, added after both #1 and #2 already
     existed, that turned out to release *neither*: its first version popped straight from the
     output ring instead of through `nextOutput()`, so a drain violation that discarded a
     `Snapshot`/`ValuesChanged` left `m_pendingPlanRefs` stuck (permanently blocking
     `dispatch()`'s own round-start guard) and a drain violation that discarded a `RequestDone`
     left that job's arena/job-ring slot un-freed (permanently, cumulatively consuming
     `adHocCapacity`). This was not caught by this developer, by the tester, or by this note's own
     first draft — SES-25 only ever exercised discarding a lone `Send` (nothing #1 or #2 cares
     about) — and was only found by the checkpoint's own fresh-eyes phase review, which traced
     both consequences by hand before a single test existed to catch them. Fixed by making
     `checkDrained()`'s discard loop call `nextOutput()` itself rather than the ring directly, so
     there is exactly one routine — not three independently-maintained ones — that knows how to
     correctly retire an `Output` of any kind; regression tests for both failure modes now exist
     (`test_session_fault.cpp`, the two "Rework (phase review blocker)" cases).

  Three subsystems needing the same guard, one of them shipping without it despite the other two
  already existing as a visible precedent, is the real lesson here: this is structural cost paid
  for zero-copy `Output`, not a one-off oversight — every *future* subsystem that hands out a
  raw-pointer view will need to remember to route its own release through the *same* place the
  existing ones do, and nothing in the type system enforces that; only re-reading `nextOutput()`
  and asking "does every other place an `Output` can leave the ring do this too" does. It is
  exactly the kind of consistency a reviewer with fresh eyes is positioned to catch precisely
  because they are not the one who wrote mechanism #1 and #2 and therefore has no reason to assume
  #3 already agrees with them.
- **`poll_plan.h`'s friend declarations exist only to carve one exception into an otherwise
  read-only public type.** `ReadPlan` grants `friend class Session` (`include/mc/core/
  poll_plan.h:262`) solely so `Session` alone can call the private `chunkForUpdate()`
  (`poll_plan.h:268`) and mutate a chunk's own `ChunkState`/`lastError`/`lastOkRound` as rounds
  run, while every other caller only ever sees `chunk()`'s `const` view. `RangeSet` similarly
  grants `friend class ReadPlan; friend class ValueStore;` (`poll_plan.h:86-87`) purely so
  `ValueStore::rebuild()` can walk the exact same private `m_entries` list `ReadPlan::build()`
  does, without either copying it or exposing it publicly. Both are narrow, well-commented, and
  contained — but they are still a hole in encapsulation that a "normal" OOP design (each type
  owns and mutates only its own data) would not need at all. They exist because the constraint
  actually driving the design is not "clean interfaces" but "zero allocation and no duplicate
  storage of the same per-point bookkeeping" — `friend` was the least-bad way to let two other
  types reach in surgically instead of copying.
- **PIMPL for every `src/`-only detail type Session owns (`OutputRing`, `AdHocQueue`) is pure
  packaging tax, not domain logic.** `include/mc/core/session.h:27-32` forward-declares both
  behind `namespace detail`, held by `std::unique_ptr<detail::X>` (`session.h:512,518`), because
  BLD-05's own include-hygiene rule (a public header may never reach a `src/`-only path) is
  absolute. The *cost*: `Session`'s move constructor/assignment and destructor cannot be the
  implicitly-defaulted ones the class would otherwise get for free — they have to be declared in
  the header and defined out-of-line in `session.cpp` (`= default` there, but *only* legal there,
  once the pointee types are complete) purely so `unique_ptr<incomplete type>`'s destructor call
  has something to call. None of this is round-scheduling, dispatch, or fault-handling logic; it
  is boilerplate that exists only because "sans-I/O, header-only-public-surface" and "hide
  implementation detail types" both apply to the same class at once.
- **The drain-contract violation handler (`src/core/session/drain_violation.h`/`.cpp`) is a whole
  indirection layer built to make one `assert()` line testable.** The spec's own wording is a
  single sentence ("debug builds assert"); reaching it honestly, without a live `assert()`
  aborting the very test process meant to prove it happens, took a replaceable function-pointer
  handler, an installer/restorer pair, and an RAII guard in the test itself
  (`test_session_fault.cpp`'s `RaiiRestoreHandler`) to avoid a failed `REQUIRE` leaking a stale
  handler into a later test case. This was not a smooth first pass, either: this developer's own
  first response to "a literal `assert()` would crash the test suite" (T-026) was to *drop* the
  debug/release split entirely rather than build the indirection — a reasonable-sounding
  simplification that the owner correctly overruled, since the spec's split is meaningful in an
  actual production debug build even though it is awkward to prove in an automated one. The
  resulting design is sound, but it is real, non-trivial machinery whose entire purpose is
  reconciling "no test-awareness in production code" with "prove this precondition check actually
  fires" — a tension that would not exist at all in a codebase willing to let assertions crash
  test binaries (many are), or one willing to skip testing this path at all (which this project's
  own rules do not permit).
- **A percentage-based coverage bar and "intentionally unreachable, defensive" code do not mix
