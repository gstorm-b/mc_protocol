- Notes for the tester:
  - Rule 4's device-number-width check reads `info.radix` from the device table for ASCII, but
    uses a fixed `Radix::Hex` for Binary regardless of the device's own radix (spec §3.4 item 4:
    "Binary ≤ FFFFFFH"/"≤ FFFFFFFFH" is a flat byte-width cap, not digit-count-in-own-radix) — this
    is why DEV-08's Binary case uses device `X` (already Hex) rather than a Dec device; the two
    limits happen to coincide in that test but are computed differently in the code, worth a close
    look.
  - Rule 3's 1E branch special-cases `L`/`S`: the device table's own `e1Code` column for L/S is
    `0x4D20` (not `kNoCode`) per spec §3.2's literal transcription, but that value is only what the
    alias *would* encode — `deviceSupportedByFamily()` does not read it directly for L/S, it
    branches on `cfg.e1AliasLS` instead. A reviewer diffing "supported ⟺ code != kNoCode" naively
    against the table would expect L/S to pass on 1E even with the alias off; they don't, by
    design (spec footnote 2, DEV-11).
  - The "T/C" (Timer/Counter) predicate for 1C field-width digits (`isTimerOrCounterDevice`) is
    derived structurally (`c1Code` length == 2) rather than from an explicit device-type list;
    worth checking it actually selects exactly {TS, TC, TN, CS, CC, CN} against the spec §3.2
    table if you want a second, independent check.
  - No `test_request.cpp` exists; `SPEC-core-model.md`'s own Project Structure table does not
    list one, so `Request`'s builders and the generic (non-DEV-ID) validate() rules were placed in
    `test_frame_config.cpp` as the only remaining test file the Plan named for this task.
