## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** the remaining `McDevice` behaviour: `linkFault` with no automatic
  reconnect, reconnect from `Faulted`, re-entrant slots, `moveToThread`,
  invalid config at connect, and the destructor.
- **Approach:**
  - Faulted state per the spec's table (transport stays open, `Session`
    discards bytes; `connectToPlc()` from `Faulted` → `linkDown`, `close`,
    `open`). No reconnect of any kind by the device (decision 7).
  - Re-entrancy: the signal queue of T-037 carries nested calls from directly
    connected slots; nothing emitted while the `Session` holds undrained outputs.
  - Destructor: closes the transport, emits nothing; if requests are still
    outstanding, one `Warn` log line with their count and ids (spec open
    question 5). Guard against signals after destruction starts.
  - `tests/device/tst_mc_device_thread.cpp` (QDV-09) — the **test** creates
    the `QThread`; the library never does. qmake twin.
- **Files expected to change:** `src/device/mc_device.cpp`,
  `include/mc/device/mc_device.h` (doc comments), `tests/device/tst_mc_device.cpp`,
  `tests/device/tst_mc_device_thread.cpp`, `tests/device/mock_plc_server.*`,
  `tests/CMakeLists.txt`, `tests/qmake/*.pro`.
- **Acceptance criteria:**
  1. QDV-05, 06, 08, 09, 11, 16, 17 pass with the expectations of the spec's
     table (QDV-11 within `effectiveTimeoutMs() + 100 ms`; QDV-17 names both
     ids in one `Warn` line and the server sees the close).
  2. QDV-13 passes for 3E ASCII (the other QDV-13 frames arrive in Phase 6).
  3. The timing tests (QDV-05, 06, 11) pass 20 times in a row on MSVC.
- **Common to every Phase 5 task:** see T-035.
- **Gate 1 approval:** 2026-09-30 — leader, under the owner's delegation
  extended to Phase 5 (`rules.md`). Gate 2: leader, one commit for the phase.

- Deviations from plan (+ reason):
  - The Plan lists `src/device/mc_device.cpp` and the header doc comments as this task's files; nearly all of the behaviour already existed from T-037 (see above), so this task's source diff is the destructor warning. Nothing was dropped.
  - Extra tests beyond the acceptance criteria (FLT-nn, CFG-DEV-01, LOG-01, THR-01, second QDV-17 function): they cover code the spec tests do not reach (the failed-write path, `TransportError`, a fault by bytes in `Idle`, `setConfig`, the pairing log). No new production behaviour was added for them.
  - QDV-11: the spec bounds only the upper limit (effectiveTimeoutMs() + 100 ms). The test also asserts a lower bound of `timeout - 2 ms` (two ms clocks truncate independently); it stops a timer that fires early. The clock starts right before `writeWords()`, whose send is what starts the Session's deadline (no subscriptions, so the send is immediate).
  - QDV-05 waits 900 ms (3 x the 300 ms timeout) with `QSignalSpy::wait`, a negative check that no connection is opened; it cannot be signal-driven. QDV-06 waits 300 ms the same way for "no retry". Both are bounded and the only fixed waits besides the ones inherited from T-035.
  - The QDV-13 frames other than 3E ASCII arrive in Phase 6, as the Plan says.

- Env notes:
  - Nothing new. QDV-06 ends on the connect timer (1000 ms here) on Windows, as noted in T-035 (a refused loopback connect takes 2 to 4 s to be reported).
  - `QMetaObject::invokeMethod(context, functor, Qt::BlockingQueuedConnection)` and the pointer-to-member overload are used in the thread test (Qt 5.10+). Borderline Qt 6.2 API: none knowingly. Used in tests: `QThread`, `QPointer`, `QSignalSpy::wait`, `QTRY_*`.
  - `QThread::finished -> deleteLater` deletes the device in its own thread; the test waits for `worker.wait()` and checks the `QPointer` (works on 6.11; documented Qt behaviour since 4.8).
- Notes for the tester:
  - The library still never starts a thread or takes a mutex (`QDV-HYG` scans `src/device`); `QThread` appears only in `tests/device/tst_mc_device_thread.cpp`.
  - `FakeTransport` is a test double; it also proves that with an injected transport `cfg.tcp.port = 0` is ignored (the FakeRig config has port 0 and validates).
  - QDV-17: the "signals after destruction" check counts emissions of a counter object outside the device across `device.reset()`; the destructor never emits (the queue is cleared, the timer stopped, the transport detached). Deleting the device from a slot connected to its own signals is not supported and is documented in the class doc (use `deleteLater()`); no test does it.
  - The mock is muted from the first connection in QDV-04/11/15/17 (`Rig(..., mute=true)`), so a request is in flight when the test acts.
