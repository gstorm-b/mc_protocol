- Deviations from plan (+ reason):
  - `include/mc/core/session.h` touched though not in the Files list — see above; unavoidable
    (private declarations/members have nowhere else to live), same as every prior Phase 3 task.
  - **Flagged for the checkpoint reviewer/owner — a real spec/build-environment tension, not
    silently resolved:** the spec's own "Drain contract" wording splits `checkDrained()`'s
    behaviour by build type ("debug builds assert; release builds discard the pending outputs
    and log at `Error`"), and even sketches it as a bare `assert()`-style call in its own "Code
    Style" section. This project's own Debug config (`build/cmake-debug`, `CMAKE_BUILD_TYPE=Debug`)
    does **not** define `NDEBUG` (only Release/MinSizeRel/RelWithDebInfo do — confirmed via
    `CMakeCache.txt`), and `build/cmake-debug` is the one every test in this repo, including
    SES-25 itself, actually builds and runs against. A literal `assert(false)` in `checkDrained()`
    would therefore abort the very build meant to catch this condition, making SES-25
    (acceptance criterion 1, and the spec's own "release" behaviour) untestable as written. I
    implemented `checkDrained()` to always take the spec's "release" branch (discard + log at
    `Error`), unconditionally, regardless of `NDEBUG` — it is the safe subset of both descriptions
    (never crashes, and is exactly what SES-25 tests), but it means a genuine drain-contract
    violation during day-to-day development will never trip a hard assert, only a log line. If a
    real debug/release distinction is wanted here, the project would need its own debug-build
    macro independent of `NDEBUG` (none exists yet). Left for the owner/checkpoint reviewer to
    decide; documented in `checkDrained()`'s own doc comment (`session.h`) and its definition
    (`session.cpp`).

- Notes for the tester:
  - The `checkDrained()` design decision above (always the spec's "release" branch, never a
    literal `assert()`) is the single most important thing to re-check independently — it is a
    deliberate, documented deviation from the spec's literal wording, not an oversight, but it is
    still a genuine behavioural choice made without the owner's explicit sign-off.
  - `faultLink()`'s three-way branch on what was actually in flight (heartbeat / ad-hoc / poll
    chunk) is worth tracing by hand against SES-16's own two subcases: the poll-chunk path marks
    `ChunkInfo`/`ValueStore` but deliberately emits **no** `Snapshot`/`CycleDone` (the round is
    abandoned, not completed — only `LinkFault` itself reports it), while the ad-hoc path reuses
    `AdHocQueue::completeInFlightChunk()` directly (not `completeAdHocResponse()`, which would
    also call `dispatch()` and try to keep sending — wrong for a fault) and the heartbeat path
    does nothing observable at all beyond `LinkFault` itself (matches "no RequestDone, ever").
  - The heartbeat's bit-parity design (`(m_round % 2) == 1` computed fresh wherever needed,
    rather than a separate stored toggle) is deliberate: it means `linkDown()`'s `m_round = 0`
    reset alone is enough to make the heartbeat sequence itself restart at bit 1 on the next
    `linkUp()`, with no separate reset logic to keep in sync — worth confirming this reasoning
    holds rather than just trusting the passing tests, since SES-16/SES-21 were not combined
    into a single "heartbeat + fault + recovery" test (each is tested only on its own).
  - `dispatch()`'s new step-2 guard (`m_currentChunk < m_plan.size()`) is unreachable except via
    a heartbeat-only round with zero polling chunks — every other path already routes around it
    (`endRound()` is called directly, or `m_roundInProgress` is already `false`, before `dispatch()`
    would ever re-enter that branch). Confirmed by inspection and by SES-21's own tests (which do
    subscribe a device, so this exact empty-plan corner isn't separately exercised) — flagging in
    case the reviewer wants a dedicated "heartbeat enabled, zero subscriptions" test added at
    Checkpoint C.
  - Receive-buffer overflow (mentioned in the leader's own task description alongside timeout/
    protocol-error/unsolicited-bytes) is implemented (`bytesIn()`'s `maxResponse` check) but has
    no dedicated SES id in the acceptance list and so has no dedicated test in
    `test_session_fault.cpp` either — it shares the same `faultLink()` path as SES-19's own wrong-
    subheader case, which does exercise `ErrorCategory::Protocol -> LinkFault{ProtocolError}`,
    just not via the overflow trigger specifically. Flagging in case Checkpoint C wants an
    explicit overflow test added.

- Files changed:

    `include/`) declaring `mc::detail::DrainViolationHandler` (a plain `void (*)()` function
    pointer), `setDrainViolationHandler(handler)` (installs it; `nullptr` restores the default),
