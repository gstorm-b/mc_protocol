## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** The shared golden-vector loader (`tests/common/vectors.h/.cpp`,
  owned by core-protocol, reused by mock and replay tests) and the
  transcription guard that catches a mistyped vector.
- **Approach:** per the module spec's "Golden vector files": `#`-prefixed
  `key: value` metadata lines (several keys per line allowed, as in the
  spec's example), one hex line per vector, an optional ASCII text line with
  `<STX>`-style control names, tags (`v1.1`, `v2`), and every metadata key
  exposed as data (`id`, `frame`, `code`, `format`, `op`, `device`, `count`,
  `kind`, `of`, `expect`, write data, tags, `bytes`). Malformed input fails
  with file name and line number. The loader is test code (may allocate) and
  lives in a small static library or object set linked by every test binary
  that needs it. Creates `mc_core_protocol_tests` (label `core_protocol`)
  with `tests/core/protocol/main.cpp`.
  - VEC-02, the transcription guard: a test that loads every `.vec` under
    `tests/vectors/` (recursively, `captured/` excluded until hil-capture
    exists) and checks that each vector's hex byte count equals its `bytes:`
    value. With only `sample.vec` today it guards that file; every later
    vector file is covered automatically.
- **Files expected to change:** `tests/common/vectors.h`,
  `tests/common/vectors.cpp`, `tests/core/protocol/main.cpp`,
  `tests/core/protocol/test_vectors_format.cpp`, `tests/vectors/sample.vec`,
  `tests/CMakeLists.txt`.
- **Acceptance criteria:**
  1. VEC-01: `sample.vec` uses every syntax element (multi-key metadata line,
     tags, request and response, ASCII line with control names, write data)
     and loads to exactly the expected records.
  2. VEC-01 negative: each malformed form (odd hex digit count, unknown
     control name, hex line without an id, bad `bytes:` value) fails with the
     file name and line number in the message.
  3. VEC-02 runs over every `.vec` file found and fails, naming the vector id,
     when a hex line's byte count differs from `bytes:` (proved once by hand
     with a deliberately wrong sample, reverted).
  4. `ctest -L "core_protocol|core_model|build"` green on MSVC.

## Dev notes  *(developer writes)*

- Files changed:
  - `tests/common/vectors.h` (new) — public API of the `.vec` loader: `VecField`, `Vector`
    (metadata fields in file order, decoded hex `bytes`, optional `text` line, `tags`, `file`,
    `line`), `VecFormatError`, and `parseVectors`/`loadVectors`/`findVectorFiles`/
    `loadAllVectors`.
  - `tests/common/vectors.cpp` (new) — the parser: metadata-line tokenizer (several `key:`
    tokens per line, value runs until the next key token), hex-line decoder (even-digit-count
    check), ASCII control-name decoder (`<STX>` etc., spec §6 debug-log notation), and the
    recursive `*.vec` finder that excludes any `captured/` path component.
  - `tests/core/protocol/main.cpp` (new) — doctest main for `mc_core_protocol_tests`, mirrors
    `tests/core/model/main.cpp`.
  - `tests/core/protocol/test_vectors_format.cpp` (new) — VEC-01 (positive round-trip of
    `sample.vec` + four malformed-input cases) and VEC-02 (transcription guard over every
    `.vec` file found under `tests/vectors/`).
  - `tests/vectors/sample.vec` (new) — five records reusing real Appendix A byte sequences
    (V-3E-B-01/02/05, V-4C1-01/02) to demonstrate every `.vec` syntax element: a multi-key
    metadata line, `tags:`, a request/response pair linked by `of:`/`expect:`, a write-data
    vector (`write:`), and an ASCII text line with control names.
  - `tests/CMakeLists.txt` — added `mc_test_vectors` (STATIC, the loader, so later `tests/mock`
    and `tests/replay` binaries can link it too per SPEC-mock-plc.md) and `mc_core_protocol_tests`
    (label `core_protocol`, links `mc::core`, `mc_doctest`, `mc_test_vectors`); the latter gets
    `MC_TESTS_SOURCE_DIR` as a compile definition so `test_vectors_format.cpp` can find
    `tests/vectors/` from the source tree regardless of which build directory (MSVC/MinGW) is
    running it.

- Deviations from plan (+ reason):
  - The `.vec` grammar itself (record = metadata block + hex line + optional ASCII text line,
    separated by blank lines) and the exact set of malformed-input checks are not spelled out
    byte-for-byte in the module spec beyond the worked example and the four required negative
    cases; I designed the parser to match the spec's own example verbatim and added two small
    extra checks beyond the four named acceptance cases: (a) an ASCII text line, when present,
    is decoded and compared against the hex line and must match (a transcription check in the
    same spirit as VEC-02, exercised implicitly by `sample.vec`'s SAMPLE-04/05); (b) a metadata
    block with no hex line following it is a distinct error. Neither changes the public
    behaviour the acceptance criteria describe; flagging in case the reviewer wants them pulled
    into their own named test IDs instead of living only as parser robustness.
  - No fixture files were added for the four malformed-input cases (odd hex digit count, unknown
    control name, hex line without an id, bad `bytes:` value): `parseVectors(text, fileLabel)`
    takes the `.vec` text directly, so the negative tests pass small inline strings with a fake
    file name instead of writing files under `tests/`. This also keeps `tests/vectors/` free of
    anything VEC-02's recursive scan would trip over (the Plan only excludes `captured/`).
  - `tests/vectors/sample.vec` is loader test data, not a protocol-core golden vector set (that
    starts at T-014/T-015 with `prim.vec`, `3e_binary.vec`, etc.); its five records are named
    `SAMPLE-01`..`SAMPLE-05`, not `V-*`, to avoid colliding with the real vector IDs those tasks
    will add under `tests/vectors/`.
  - Reasonable, in-Plan file: no `src/` or `.pri` change (T-013 adds no library code), so BLD-04
    pri_sync and BLD-05 include_hygiene are unaffected (both scan only `include/` and `src/`).

- Env notes (new facts about the build environment, for build-env.md):
  - A test binary that needs to find files under the source tree at runtime (here,
    `tests/vectors/`) cannot rely on its own working directory: ctest runs each binary from its
    own build tree, and `build/cmake-debug` vs. `build/cmake-mingw` sit at different depths under
    the repo root, so a relative path baked into the test would not be portable between the two
    daily-loop trees. The pattern used here: `target_compile_definitions(<test target> PRIVATE
    MC_TESTS_SOURCE_DIR="${CMAKE_CURRENT_SOURCE_DIR}")` in `tests/CMakeLists.txt`, read back as
    `std::filesystem::path(MC_TESTS_SOURCE_DIR) / "vectors"` in the test. No existing test
    binary needed this before T-013; worth keeping as the standard way to do it if a later
    module test needs its own fixture directory.
  - MSVC `/WX` catches `C4457` (local variable hides function parameter) — not yet hit by
    T-001..T-012; straightforward to avoid (distinct names), noting it here since it is easy to
    reintroduce when a function's parameter and a natural local variable name coincide (e.g.
    `text`, `data`, `value`).

- Notes for the tester:
  - Checkpoint B (T-019) should independently re-run the VEC-02 "proof" (criterion 3) itself
    rather than trust this note: edit any `bytes:` value in any checked-in `.vec` file, confirm
    `mc_core_protocol_tests` fails naming that vector's id, then confirm the revert restores a
    green run.
  - `tests/vectors/sample.vec`'s SAMPLE-04/05 pair (format `3C` F1, tagged `v2`) exercises the
    ASCII/control-name path even though 3C itself is out of v1 scope for `core-protocol`'s own
    codec tests (T-018) — it is only exercising the *loader*, not a claim that 3C encoding
    exists yet.
  - The loader treats `id` as the only mandatory metadata key; everything else (`frame`, `code`,
    `op`, `device`, `count`, `kind`, `of`, `expect`, `write`, `format`, `tags`, `bytes`) is a
    plain string the loader does not interpret — parsing "count: 3" into an int, "device: D100"
    into a `Device`, etc. is each consumer's own job (T-014 onward, and later `tests/mock`).
  - Hex digits in a `.vec` file may be upper or lower case; the loader does not enforce the
    reference spec's upper-case-on-encode rule (that rule belongs to `hexascii` under test in
    T-014, not to this file-format loader).
