- Deviations from plan (+ reason):
  - **Touched `include/mc/core/poll_plan.h`** (not in this task's file list): added a private
    `ChunkInfo& chunkForUpdate(size_t)` and `friend class Session;` to `ReadPlan`. Necessary gap
    found while implementing: the spec's own text describes `ChunkInfo::state`/`lastError`/
    `lastOkRound` as live fields a running `Session` updates every round ("0 = never read
    successfully **since linkUp**"), but T-020's `ReadPlan` (already accepted) only exposes
    `const ChunkInfo& chunk(size_t) const` — no way for anything outside `ReadPlan` to record a
    chunk's own outcome. Mirrors the `RangeSet`/`ValueStore` friend pattern already in this file
    from T-020/T-021: minimal, additive, external observers still only ever see `ChunkInfo`
    through the existing `const` accessor.
  - **This task's own scope, as I read the Approach text and the Files list together, is
    narrower than `session.h`'s full public surface** (which I had to write completely regardless
    — see "Files changed" above for why). What's genuinely implemented vs. deliberately stubbed,
    all noted in the code itself (session.h/session.cpp's own comments) and repeated here for
    visibility:
    - `submit()` validates and chunks the request (same errors the real thing would give) and
      checks `isLinkUp()`, but always answers `QueueFull` when it would otherwise succeed: no
      ad-hoc arena exists yet (`adhoc_queue.h/.cpp` is explicitly T-025's own file, not in this
      task's list). This is a genuine, documented `submit()` error path — not a fabricated one —
      and it never hands out an id, so "exactly one `RequestDone` per accepted `submit()`" is
      never at risk (nothing was accepted). T-025 replaces this whole function body.
    - `bytesIn()` treats every `Parser::Failed` outcome identically (mark the chunk `Failed`,
      keep polling): it does not yet distinguish "PLC error, no retry" from "protocol error /
      timeout, Ethernet `LinkFault`" (spec's fault table) — that distinction, and the whole
      Ethernet fault path (`LinkFault` output, `maxConsecutiveLinkErrors`, `reopenTransport`), is
      explicitly T-026's job. `tick()` does not enforce the response deadline (`Waiting` state)
      for the same reason.
    - `ValueStore::apply()`/`markFailed()` are never called from `bytesIn()`/
      `completeCurrentChunk()` in this task: decoding into the store and the whole "Publishing
      values" contract (`ValuesChanged`/`Snapshot`, decisions S1-S5) is explicitly T-023's own
      Approach ("as the module spec's 'Publishing values (decisions S1-S5)', exactly").
      `ChunkInfo::state`/`lastError`/`lastOkRound` ARE tracked now (see the `poll_plan.h`
      deviation above), since round-scheduling itself needs to know success/failure regardless
      of value publishing.
    - The heartbeat write (`SessionConfig::heartbeat`) is never consulted by `dispatch()`/
      `startRound()`: `CycleInfo::heartbeatOk` is hard-coded `true`. `SES-21` is T-026's own
      criterion.
    - The drain-contract precondition (`nextOutput()` must be fully drained before the next
      input call) is documented (`@pre` on every input method) but not asserted/enforced: `SES-25`
      is explicitly T-026's own criterion ("the drain-contract check").
    - Ad-hoc priority (dispatch step 1) is skipped entirely: with no ad-hoc queue, there is
      nothing to check.
    - Serial (`Flushing` state, EOT, flush, inter-character deadlines) is declared in the `State`
      enum for completeness but never reached; 3E/Ethernet only, matching every other Phase 3
      task's own scope so far.
  - **`dispatch()` never recurses**, even for an empty plan at `cycleIntervalMs == 0` (worked
    through by hand, not covered by a named SES test): spec's "a round with no chunks still runs
    ... and still emits `CycleDone`" plus "interval 0 = rounds back-to-back" could otherwise mean
    an unbounded, synchronous `CycleDone` stream within one input call, which the output ring
    (fixed capacity, "sized for the worst **single** call") cannot support. Resolved as: a round
    with chunks reaches `sendChunk()`, which is a natural stopping point (produces one `Send`,
    enters `Waiting`) — so "back-to-back" for a real (non-empty) round already falls out for
    free, with no extra recursion, and is exactly what `SES-07`'s interval-0 `SUBCASE` and the
    130ms-round `SUBCASE` both exercise (a round's own completion immediately produces the next
    round's `Send`, in the same call). Only the genuinely degenerate empty-plan-and-interval-0
    case is capped at one round per input call. Flagging for the leader/owner since it is a
    judgment call the spec text does not spell out either way.
  - `SessionConfig::validate()` only checks `heartbeat.device` (when `heartbeat.enabled`) against
    `frame`, reusing `mc::validate()`. The sketch names no other constraint on `SessionConfig`'s
    other fields, so I did not invent any.
  - `output_ring.h`'s own "+ change arena" (its name in the module spec's Project Structure) is
    not built: nothing in this task ever produces a `ValuesChanged`/`Snapshot` output whose raw
    pointers would need it. Flagged in the file's own comment for T-023 to extend.

  - Confirmed on a **leaf** qmake project (not a `subdirs` one): editing an existing `.pro`'s
