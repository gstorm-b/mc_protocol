## Dev notes  *(developer writes)*

- Files changed:
  - `src/core/protocol/device_encode.h` / `.cpp` (new) — `qnaDevice()` (3E/3C: ASCII/Binary x
    Q/L/iQ-R), `e1Device()` (1E: ASCII/Binary) and `c1Device()` (1C, always ASCII: ACPU/AnA-AnU),
    plus `qnaDeviceSize()`/`e1DeviceSize()`/`c1DeviceSize()`. Built on core-model's `deviceInfo()`
    (spec §3.2 table, already implemented) for each family's own code, and on `field_codec.h`'s
    `AsciiCodec`/`BinaryCodec` (`putU16`/`putU32`) wherever a field is plain hex/LE — `e1Device()`
    is entirely expressed that way. The one new primitive is `putFixedWidthNumber()` (private to
    `device_encode.cpp`): a device number zero-padded to a fixed width in the device's own radix
    (decimal or hex) — needed by QnA ASCII and 1C, neither of which field_codec.h's hex-only
    u16/u32 can produce.
  - `src/CMakeLists.txt`, `mc_core.pri` — the new header/source pair added to `mc_core` in the
    same change (BLD-04).
  - `tests/core/protocol/test_device_encode.cpp` (new) — DEV-07 (wire half): 40 `SUBCASE`s (5
    devices x 8 families) reproducing every cell of spec §3.3's example table, plus two more
    `TEST_CASE`s for acceptance criteria 2 (padding, implicit in the exact byte/character
    comparisons — see "Notes for the tester") and 3 (`InvalidDevice` on a device the family has
    no code for, `BufferTooSmall` on an undersized destination).

- Deviations from plan (+ reason):
  - **`e1Device()` has no `aliasLS`/alias parameter.** The Plan and the module spec both name
    "e1Device()" without fixing its signature. Checking `src/core/model/device_table.cpp`
    (already implemented, Phase 1) shows `DeviceType::L` and `DeviceType::S` already carry
    `DeviceType::M`'s own `e1Code` (`0x4D20`) in the table *unconditionally* — the alias is baked
    into the data, not something this function chooses. `validate()` (core-model,
    `validate.cpp:106-117`) is what actually gates it: an `L`/`S` device reaches a 1E frame at all
    only when `FrameConfig::e1AliasLS` is set, before `e1Device()` ever runs. So `e1Device(d,
    code, out)` just uses `deviceInfo(d.type).e1Code` directly, with no branching for L/S and no
    parameter for the flag — simpler than guessing a shape, and correct because the check already
    happened one layer up.
  - **No explicit device-number-overflow check inside `device_encode.cpp`.** Same reasoning as
    T-014's field_codec.h note: `validate()` already rejects an oversized device number
    (`InvalidDevice`) before `McProtocol::encode()` calls any codec, so `putFixedWidthNumber()`
    has a documented precondition (the number fits `width` digits) rather than a runtime check.
    What *is* checked here, because it is a property of `d.type` alone that `validate()` does not
    decide, is whether the family has any code at all for `d.type` (spec §3.2's blank table
    cells) — that is DEV-07 acceptance criterion 3.
  - **QnA Binary Q/L's 3-byte little-endian number is written directly (three explicit shifts),
    not through a borrowed 4-byte `field_codec.h` helper.** No primitive in `field_codec.h` is 3
    bytes wide (u8/u16/u32 only); reusing `BinaryCodec::putU32` into a 4-byte scratch buffer and
    discarding one byte would have been more indirect than just writing the 3 bytes, so this one
    field is new, not duplicated, code.

- Notes for the tester:
  - Acceptance criterion 2 ("* padding and zero padding explicitly, no spaces anywhere") has no
    separate assertion of its own: `checkAscii()` compares the *entire* expected string
    byte-for-byte (e.g. `"D***00000100"`, `"TN010"`), so a space-padded or lower-case
    implementation already fails the existing DEV-07 `SUBCASE`s — proved by hand above (Commands
    run). A reasonable independent check: repeat that same hand-proof (or a variant, e.g. `'*'`
    padding instead, or lower-case hex) rather than trusting this note, then confirm the revert
    restores green.
  - `qnaDevice()`/`e1Device()`/`c1Device()` take `DataCode`/`PlcSeries`/`C1CommandSet` as
    ordinary runtime parameters (an if/else inside device_encode.cpp), not a `Codec` template
    parameter like `field_codec.h`'s functions — the module spec explicitly allows this ("no
    ASCII/Binary branches inside command code except device encoding"), and a QnA-ASCII code
    field is a raw text-table copy with no Binary equivalent to share, so the `AsciiCodec`/
    `BinaryCodec` template pattern would not have reduced any duplication here.
  - `field_codec.h` is unchanged by this task; `device_encode.cpp` only calls its existing
    `putU16`/`putU32`, nothing new added to it.
