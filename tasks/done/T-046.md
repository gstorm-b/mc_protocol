## Dev notes  *(developer writes)*

- Files changed:

    `frameSerialEncodedSize/Encode` (`ENQ` + `"F9"` station network PC self-station + 0401/1401 request
    data from `qnaRequestData<AsciiCodec>` + SUM over "after ENQ .. end of request data" + `CR LF`
    in F4), `frameSerialMaxResponseSize` (max of the expected frame and the NAK frame),
    `frameSerialTryParse` (T-045's `serialFeed`, then frame ID always, access route when
    `cfg.checkRoute`, read needs a data frame of exactly `qnaResponseDataSize`, write needs an ACK, NAK ->
    `Plc` error with `plcCode` = the 4-character code), `frameSerialPayload`,
    `frameSerialFormatSupported` (F1 and F4 only; T-047 widens it).
  - `src/core/protocol/protocol.cpp`: `isImplemented()` true for `F3C` + Ascii + a supported format;
    serial frames dispatch before the codec choice in `encodedSize`, `encode`, `maxResponseSize`,
    `Parser::feed` (the `SerialCursor` lives in the existing `m_frameLength` (scan position, only
    while `NeedMore`) and `m_skipped`) and `Parser::payload`. 3E/1E paths unchanged.
  - `src/CMakeLists.txt`, `mc_core.pri`: `frame_serial.cpp/.h`.
  - `tests/vectors/3c_f1.vec`, `3c_f4.vec` (new): 23 records each = the 5 spec rows (A.12 / A.15) +
    18 derived rows. Enabled 23 + 23, tagged 0. Derived rows: G2 / G3 / G6 requests and responses,
    iQ-R word and bit requests, sum-off request and response (4C-10), wrong station (4C-13) with and
    without `checkroute: off`, frame ID F8, wrong SUM (4C-09), data one character short, ACK to a read,
    data to a write, NAK (`C051`) to a write.
  - `tests/core/protocol/test_frame_serial.cpp` (new): 3C-01 (F1, F4 over the vector files, SZ-01,
    each vector also fed byte by byte), 3C-02, hand-derived non-default route, 4C-09, 4C-10, 4C-13,

  - `tests/core/protocol/serial_vector_config.h` (new, test helper): metadata of a serial record ->
    `FrameConfig` / `Request` (keys `series`, `sum`, `block`, `checkroute`, `blockcheck`, `f3shortsum`).
  - `tests/core/protocol/test_parser_stream.cpp`: STR-01 pool includes `3c_f1/3c_f4`; new STR-02

- Deviations from plan (+ reason):
  - `test_frame_3e.cpp`, `test_parser_stream.cpp`, `test_alloc.cpp` and `serial_vector_config.h` are not in
    the Plan's list: the first breaks once 3C works, the next two are where the module spec puts
    STR-01/02/04 and ALC-01 ("extend ALC-01 once the frames exist", T-045), the last is shared by two
    test files.
  - The derived vector rows (18 per file) are not in Appendix A; their bytes and SUMs were produced by a
    one-off perl script from the spec's format table and sum ranges (it also re-verifies the SUM of every
    spec row it copies, and that each spec row's text line equals its hex line). The script is not
    part of the tree. Spec rows were extracted from the spec text by the same script (hex, text line, byte
    count), not retyped.
  - SZ-01 (`length <= maxResponseSize()`) is checked on every success row and on `Plc` error rows, not on
    the derived rows that are wrong by size (data to a write): they are not responses a PLC may
    send, and the bound is about those.
  - `frameSerialTryParse` failure `frameLength`: the whole frame in every case except a Format 3 malformed
    body (T-045: through ETX). Judging order: SUM and terminator (T-045), then frame ID, route, then
    kind/size; a NAK from another station is `FrameMismatch`, not a PLC error.
  - `McProtocol` with `F3C` and `code == Binary` (an invalid config) reports `UnsupportedCommand` (tested),
    the way `maxResponseSize() == 0` reports unimplemented; it does not return the `InvalidConfig` error
    the `McProtocol` class doc promises for configs failing `validate()`. The 3E/1E paths do not either
    (nothing calls `cfg.validate()` inside `McProtocol`); left as is, reported here.
