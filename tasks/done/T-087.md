  - The reference spec's Q3 had decided "exactly N, no padding". The leader has amended these, per the owner's decision; do not edit them:
    - `docs/mc_reference/mc-protocol-frame-spec.md` and `.vi.md` (§2.2 table, Q3);

- **Goal:** the client encoder appends one `'0'` (30H) after the N data characters of a 1E ASCII batch bit write (02H) when N is odd. The mock (server direction) expects it. Nothing else changes: 1E Binary nibble padding, QnA, 1C (manual §7.4 BW has no such rule), and reads.
- **Approach:**
  1. **Encoder** (`src/core/protocol/`, find the 1E ASCII bit-write data path; `bit_payload.h` / `command_a1e.cpp` / `frame_1e.cpp`):
     - Append the dummy for odd N.
     - `encodedSize()` must agree with the new length, because the ad-hoc arena relies on it.
     - No allocation change.
  2. **Validation and limits:** the 1E field maximum stays 256 points. Check nothing else counts the data length (the response parser does not).
  3. **Mock** (`src/mock/request_decode_ethernet.cpp`): compute the 1E ASCII 02H request length as N + (N mod 2) characters. A frame with only N characters stays incomplete, with no answer, as the spec paragraph says.
  4. **Tests:**
     - 1E-15 in the core-protocol tests: N = 1 → data `"1"` + `"0"`; N = 5 → `"10101"` + `"0"`; N = 8 → no dummy. Use literals worked out by hand.
     - MCK-14 in the mock tests.
     - INT-03 (`write_bits` with odd count 5 → read back) must pass on 1E ASCII through `Session` ↔ `MockPlc`.
     - Golden vectors from Appendix A are **never edited**. If any Appendix A vector encodes a 1E ASCII odd bit write without the dummy, do not change it. Report it, and propose how it is tagged (supersede note), in the Dev notes.
  5. **Replay:** the existing captures are not in `tests/vectors/captured` yet (T-089 imports them), so there is nothing to tag here. Note for T-089: RPL-01 will differ on the odd 1E ASCII writes captured with 0.1.2, because the capture has no dummy and the encoder now adds one.
