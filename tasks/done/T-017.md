## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** The first end-to-end codec slice: the public
  `include/mc/core/protocol.h` (`McProtocol`, `Parser`, `ParseStatus`),
  dispatch by `FrameType`, and the 3E envelope and response parse in Binary.
- **Approach:** exactly the module spec's `protocol.h`, "Internal design"
  (switch on the frame enum, no virtual dispatch; `Parser` fixed-size with a
  cursor over the caller's buffer) and "Error mapping". `encode()` always
  runs `validate(Request, FrameConfig)` first. Frame types not implemented
  yet (1E, 3C, 1C) return `UnsupportedCommand` from `encode`/`parser` until
  their tasks land — never undefined behaviour. `protocol.h` is the contract
  Phases 3 and 4 build on; the owner reviews it at Checkpoint B.
- **Files expected to change:** `include/mc/core/protocol.h`,
  `src/core/protocol/protocol.cpp`, `src/core/protocol/frame_3e.h`,
  `src/core/protocol/frame_3e.cpp`, `src/CMakeLists.txt`, `mc_core.pri`,
  `tests/CMakeLists.txt`, `tests/vectors/3e_binary.vec`,
  `tests/core/protocol/test_frame_3e.cpp`.
- **Acceptance criteria:**
  1. Every A.1 vector round-trips: requests byte-for-byte; responses to the
     stated payload or `Error`.
  2. 3E-01…13 pass for Binary; SZ-01 holds for every 3E Binary vector.
  3. `static_assert(sizeof(Parser) <= 128)` and `Parser` trivially copyable.
  4. `protocol.h` exposes only `McProtocol`, `Parser`, `ParseStatus`;
     `ctest -L "core_protocol|core_model|build"` green on MSVC.

## Dev notes  *(developer writes)*

- Files changed:
  - `include/mc/core/protocol.h` (new, public) — `ParseStatus`, `Parser`, `McProtocol`, exactly
    the module spec's sketch (checked it compiles as declared before writing anything else, per
    the T-007 lesson — it does, unmodified), with full `docs/rules/doc_comment_style.md` doc
    comments and the two `static_assert`s (`sizeof(Parser) <= 128` -- actual `sizeof(Parser) ==
    96`; `std::is_trivially_copyable_v<Parser>`). No other symbol is exposed at namespace scope.
  - `src/core/protocol/protocol.cpp` (new) — `McProtocol`'s methods (dispatch on
    `FrameConfig::frame`/`code`; only `F3E` + `DataCode::Binary` is implemented) and `Parser`'s
    methods (`feed`/`payload` dispatch the same way; `frameLength`/`skipped`/`error`/`reset` are
    plain accessors/resets). One private frame-independent helper, `normalizedPayloadSize()`
    (the "Payload contract"), backs both `McProtocol::payloadSize()` and `Parser::payload()`'s own
    output-size check.
  - `src/core/protocol/frame_3e.h` / `.cpp` (new) — `frame3eEncode<Codec>()`/
    `frame3eEncodedSize<Codec>()` (spec §5.1 request envelope, built on command_qna.h's request
    data) and `frame3eTryParse<Codec>()`/`frame3eMaxResponseSize<Codec>()` (response envelope:
    subheader/route check, length field, end code, error information per spec §7.2). Explicitly
    instantiated for `BinaryCodec` only; see "Deviations" for why `AsciiCodec` is not instantiated
    at all yet, not merely untested.
  - `src/core/protocol/field_codec.h` — added `BinaryCodec::putFixed`/`matchesFixed` and
    `AsciiCodec::putFixed`/`matchesFixed` (spec E1, fixed byte-string fields: the 3E subheader),
    exactly the extension T-014's own Dev notes anticipated. Each takes both a binary and an
    ASCII literal and uses only the one that matches its own codec (module spec's frame_3e.cpp
    Code Style example keeps the two literals separate, not one derived from the other).
  - `src/CMakeLists.txt`, `mc_core.pri` — the three new header/source pairs (`protocol.cpp` has
    no header of its own; it implements the existing public `protocol.h`) added to `mc_core` in
    the same change (BLD-04).
  - `tests/vectors/3e_binary.vec` (new) — every Appendix A.1 vector (`V-3E-B-01`..`13`;
    `V-3E-B-13`, the 0403 command, tagged `v1.1`), plus six records for the derived cases spec
    §9.6 describes but does not give as their own Appendix A vectors (`3E-08`..`3E-13`: wrong
    subheader, length < end code, wrong payload size, error without info, other station,
    multiple CPU) — see "Notes for the tester" for exactly how each was derived.
  - `tests/core/protocol/test_frame_3e.cpp` (new) — a `kind:`-dispatched reader for
    `3e_binary.vec` covering 3E-01, 03..13 and SZ-01 (3E-02 is ASCII, T-018's own task), plus two
    standalone `TEST_CASE`s: `checkRoute` (spec §5.1's optional route check; no 3E-xx ID names
    it) and `UnsupportedCommand` (proving `encodedSize`/`encode`/`maxResponseSize`/`parser`/feed
    never reach undefined behaviour for `F1E` or for 3E ASCII, and that `payloadSize()` alone
    stays correct regardless).

- Deviations from plan (+ reason):
  - **`maxResponseSize()`/`payloadSize()`/`parser()` have no `Expected<>` return, unlike
    `encodedSize()`/`encode()`, so "not implemented yet" needed its own convention** (the module
    spec's sketch does not say what these three do for an unsupported frame — an underspecified
    edge case, not a contradiction, but one this header's Checkpoint B review should confirm):
    `maxResponseSize()` returns `0`; `parser()` returns a `Parser` whose first `feed()` call
    immediately returns `Failed` with `UnsupportedCommand` (`frameLength() == 0`, nothing
    examined); `payloadSize()` is unaffected because it turned out to need no frame dispatch at
    all (next bullet). Documented directly on `McProtocol`'s class comment and each affected
    method, and proved by the `UnsupportedCommand` `TEST_CASE`.
  - **`McProtocol::payloadSize()` and `Parser::payload()`'s own bounds check share one
    frame-independent helper, `normalizedPayloadSize()`, not part of the `FrameType` dispatch.**
    The Payload contract (protocol.h's own doc, unchanged from the module spec) depends only on
    `Request::op`/`count`/`bitLayout` -- never on which frame family or wire code -- so this
    function never fails and never needs a per-frame implementation; 1E/3C/1C will reuse it
    unchanged rather than each defining their own.
  - **`frame_3e.cpp` explicitly instantiates `frame3eEncode`/`frame3eTryParse` for `BinaryCodec`
    only.** 3E ASCII is T-018's own task (its Plan and title both say so); leaving `AsciiCodec`
    uninstantiated means `protocol.cpp`'s dispatch (which already gates on
    `cfg.code == DataCode::Binary` before calling either function) could not reach unproven code
    even by a dispatch bug -- a link error, not a runtime one, backs up the `isImplemented()`
    check. `command_qna.cpp` (T-016) already established this same explicit-instantiation
    pattern.
  - **`Parser` stores a full `FrameConfig` by value (40 bytes) rather than copying out only the
    2-3 fields 3E currently needs.** Considered a flatter, hand-picked field set first, but
    `sizeof(FrameConfig) == 40` leaves comfortable room under the 128-byte cap (measured
    `sizeof(Parser) == 96`), and storing the whole config means `frame_1e.cpp`/`frame_serial.cpp`
    (1E, 3C, 1C) can read whatever fields *they* need (`commandSet`, `messageWait`, `sumCheck`,
    `format`, ...) without Parser's own layout changing again -- one struct copy now instead of a
    growing hand-maintained field list later.
  - **`Parser`'s internal state is a flat struct, not a literal C++ `union`**, even though the
    module spec's Project Structure line for `protocol.cpp` says "Parser state union". Only 3E's
    state exists as real, tested code this task; a `union` (or a tagged variant) sized for
    hypothetical 1E/3C/1C state that does not exist yet would be exactly the untested, speculative
    code the Definition of Done rules out. `sizeof(Parser) <= 128` leaves headroom for this to
    become a real union later if a flat struct ever stops fitting; flagging so the reviewer knows
    this is a considered simplification, not an oversight of that line.
  - **3E-03 ("length fields... every 3E/4E vector") and SZ-01 have no test of their own beyond
    what 3E-01/04..13 already assert.** A request/response's length field is part of the exact
    byte sequence `checkRequestVector`/`checkResponseVector` already compares in full, so a wrong
    length field is already a failing assertion in each of those; SZ-01 (`encodedSize() ==` vector
    length, response length `<= maxResponseSize()`, payload length `== payloadSize()`) is checked
    inline in the same two helper functions, for every non-`v1.1` vector, rather than as a
    separate pass over the file.
  - **`3E-08`..`3E-13` are derived, not literal Appendix A vectors** (spec §9.6 gives them as a
    modification of an existing vector or a fresh byte string, not as their own `V-3E-B-*` ID);
    each was hand-built from the reference's own stated recipe and its byte count independently
    recomputed with `bash`/`wc -w` before being typed into `3e_binary.vec` -- see "Commands run".
