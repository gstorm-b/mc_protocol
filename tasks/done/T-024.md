## Plan  *(leader writes; Gate 1 approves)*

  boundary (decision 10).
- **Approach:** deferred re-plan at the round boundary; values and baselines
  carried over through `ValueStore::rebuild()`; the current round is never
  re-planned mid-way.
- **Files expected to change:** `src/core/session/session.cpp`,
  `tests/core/session/test_session_poll.cpp`.

## Dev notes  *(developer writes)*

- Files changed:
  - `src/core/session/session.cpp` — `dispatch()`'s round-start branch now defers starting a
    round (staying `Idle`) when a re-plan is pending and `m_pendingPlanRefs > 0`; `nextOutput()`
    decrements that counter when it pops a `Snapshot`/`ValuesChanged`; top comment and
    `applyRePlan()`'s own comment updated.
  - `src/core/session/session_rx.cpp` — `emitSnapshot()` and the `ValuesChanged` push in
    `completeCurrentChunk()` each increment `m_pendingPlanRefs` right before pushing.
  - `tests/core/session/test_session_poll.cpp` — added, in this order (matching how they were
    written: regression test first, then the fix, then the rest):
    - `"T-024 2a regression: ..."` — acceptance criterion 2a's own regression test; written and
      confirmed failing *before* touching any production code (see "Commands run" below for the
      exact failure).
    - `"T-024 2: a subscription made mid-round leaves the current round's remaining chunks and
      outputs unchanged"` — acceptance criterion 2's own test: a two-chunk round, `subscribe()`
      called between the two chunks, checks the *second* chunk's sent bytes are byte-identical to
      what they would have been without the pending re-plan.
    - `"SES-22 ..."` — subscribe and unsubscribe each mid-round, across four rounds: current
      round unaffected both times, next round picks up the change, and the newly subscribed
      device's first-ever read (round 2, i.e. not round 1) is silent (decision S4) even though
      `m_round >= 2`.
  - `include/mc/core/session.h` — **not in this task's file list**: one new private member,
    `size_t m_pendingPlanRefs{0}`, and doc-comment updates on `dispatch()`/`nextOutput()`'s
    surrounding text. See "Deviations".

- Deviations from plan (+ reason):
  - **Touched `include/mc/core/session.h`** (not in this task's file list, same as T-023's own
    `m_payloadBuf`/`m_changeBuf` addition): the fix needs a way for `dispatch()` to know whether
    a `Snapshot`/`ValuesChanged` pushed earlier in *this same call* is still sitting undrained in
    the output ring before it is safe to apply a pending re-plan. `m_pendingPlanRefs` is that
    counter; it is `private` and touches no public-facing behaviour.
  - **Chosen fix, and why, per your instruction to choose between "defer `applyRePlan` until the
    ring is drained" or "keep the previous plan alive until then":** deferring is what I built,
    but not by checking "is the ring empty" (it never is at that point — `endRound()` always
    pushes `CycleDone` first, so that check would silently disable *all* back-to-back scheduling,
    breaking SES-07's own interval-0/130ms `SUBCASE`s). Instead, `m_pendingPlanRefs` counts
    specifically the outputs whose validity actually depends on `m_plan`/`m_changeBuf`
    (`Snapshot`, `ValuesChanged`) — `dispatch()` only defers the round start when a re-plan is
    pending *and* at least one of those is still queued. This is more precise than "ring empty"
    and needed no new state beyond the one counter; "keep the previous plan alive" (a retired-
    plans list, freed once drained) would also have worked but is more moving parts for the same
    guarantee, so I did not build it.
  - **Observable behaviour change (worth the leader/owner's attention, not hidden):** when a
    re-plan is pending *and* the next round is due immediately (back-to-back scheduling), the new
    round now starts one input call later than it used to (T-023's own behaviour) — the caller's
    very next call, which per the drain contract must come after draining, is what actually
    starts it. `nextDeadline()` still correctly reports "due now" throughout, so a well-behaved
    caller (per the spec's own non-Qt usage example, which always calls `tick()`/`bytesIn()` again
    immediately when `now >= nextDeadline()`) sees this as, at most, one extra harmless loop
    iteration — never a missed or duplicated round. No named SES test asserts the *exact* call
    a re-plan applies on, only that it applies "at the next round boundary" (decision S6), which
    this still satisfies.

- Notes for the tester:
  - The three new test cases are in `tests/core/session/test_session_poll.cpp`, immediately
    after `SES-06` (the 2a regression and criterion-2 tests) and immediately after that
    (`SES-22`).
  - The 2a regression test reads the queued `Output`s directly via `session.nextOutput()`,
    deliberately bypassing `OutputRecorder`'s own deep-copy — that copy itself happens *after*
    the corruption window, so going through it would have masked the bug rather than caught it.
    Worth keeping that pattern in mind for any future test of a similar "does this pointer survive
    until drained" question; `OutputRecorder` is the right tool for everything else.

    call later than before) is the one thing here I'd want a second pair of eyes on at
