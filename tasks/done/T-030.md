## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** `MockPlc` configured for 3E Binary or 3E ASCII decodes requests
  and builds responses from the reference spec's tables, pinned to the golden
  vectors read in the reverse direction.
- **Approach:**
  - `src/mock/request_decode_ethernet.cpp`: 3E framing by the
    request-data-length field, any fragmentation, several requests in one
    buffer; bytes that cannot start a request (wrong subheader) get no
    response and an unanswered log record (spec "Ethernet reception").
    Device layout chosen from the **received** subcommand (0000/0001 Q/L,
    0002/0003 iQ-R). Commands 0401/1401 only; anything else is answered with
    `MockOptions::unsupportedQna` (the MCK-09 test itself is T-031).
  - `src/mock/command_exec.cpp`: batch read/write on the memory image;
    out-of-range per `setDeviceLimit` → `outOfRangeQna`; `failRange` lookup
    (the store exists from T-029; making it answer is here, since MCK-03
    needs it).
  - `src/mock/response_build.cpp`: 3E header, response data length, end code,
    data or error information (route + command + subcommand, as V-3E-B-10
    shows); the response **echoes the request's route**; odd bit reads pad the
    low nibble with zero (binary) as V-3E-B-09 shows.
  - `tests/mock/test_mock_vectors.cpp` iterates the 3E Binary and 3E ASCII
    vector files through `tests/common/vectors.h` (metadata as data), naming
    the vector ID on failure. Vectors tagged `v1.1`/`v2` are skipped the way
    `mc_core_protocol_tests` skips them.
  - `tests/mock/check_mock_includes.cmake` (MCK-HYG) as a ctest script test
    under label `mock`, plus a negative control proving it fails on a source
    that includes `core/protocol/frame_3e.h` (e.g. a fixture directory fed to
    the script, `WILL_FAIL`) — the real `src/mock` is never edited to prove it.
- **Files expected to change:** `src/mock/request_decode_ethernet.cpp`,
  `src/mock/command_exec.cpp`, `src/mock/response_build.cpp` (plus private
  headers they need), `src/mock/mock_plc.cpp`, `src/CMakeLists.txt`,
  `mc_mock.pri`, `tests/mock/test_mock_vectors.cpp`,
  `tests/mock/check_mock_includes.cmake` (+ fixture), `tests/CMakeLists.txt`,
  `tests/qmake/mc_mock_tests.pro`.
- **Acceptance criteria:**
  1. MCK-01 for A.1 and A.2: every enabled 3E request vector decodes to the
     op, head, count, series and write data of its metadata (checked through
     `requests()` and memory).
  2. MCK-02 for A.1 and A.2: with memory seeded from the metadata, every
     success response vector is reproduced byte-for-byte.
  3. MCK-03 for 3E: V-3E-B-10 and V-3E-A-10 reproduced with `failRange`
     (C051H + error information).
  4. MCK-12 end-to-end on 3E: a request reaching the device limit gets
     `outOfRangeQna`; one ending below it succeeds.
  5. Ethernet parts of MCK-05, MCK-07, MCK-10 (added by the leader; the
     todo assigns their serial/1E parts to T37/T44): every 3E request vector
     fed one byte at a time and two requests back-to-back decode identically;
     a non-default request route is echoed; V-3E-B-09 (zero low nibble) is
     reproduced.
  6. MCK-HYG green, and its negative control proves a `frame_3e.h` include
     makes it fail.

## Dev notes  *(developer writes)*

- Files changed:
  - `src/mock/mock_internal.h` (new, private header): `Route`, `QnaRequest`, `DecodeResult`,
    `Fault`, `Outcome` and the three server-direction entry points.
  - `src/mock/request_decode_ethernet.cpp` (new): 3E framing by the request-data-length field
    (subheader check first, then the fixed header, then `len` bytes), decoding of 0401/1401 with
    subcommands 0000/0001 (Q/L) and 0002/0003 (iQ-R), device fields decoded from the device table
    (`deviceInfo()`), fields read through `AsciiCodec` / `BinaryCodec` of `field_codec.h`.
  - `src/mock/command_exec.cpp` (new): batch read/write on the memory image, `failRange` lookup,
    limit lookup, response-size check.
  - `src/mock/response_build.cpp` (new): 3E response (subheader `D0 00` / `"D000"`, echoed
    route, length, end code, data or error information route + command + subcommand).
  - `src/mock/mock_plc.cpp`: `bytesIn` now frames requests from the receive buffer, logs them,
    executes them and queues responses; junk handling; request log records.
  - `src/CMakeLists.txt`, `mc_mock.pri`: the four new files (BLD-04 green).
  - `tests/mock/test_mock_vectors.cpp` (new, 21 test cases): MCK-01, MCK-02, MCK-03, MCK-12
    end to end, and the 3E parts of MCK-05, MCK-07, MCK-10, driven by `3e_binary.vec` and
    `3e_ascii.vec` through `tests/common/vectors.h`, naming the vector ID on failure; hand-built
    frames (from spec §5.1) for the cases the vectors do not cover.
  - `tests/mock/check_mock_includes.cmake` (new, MCK-HYG) and `tests/mock/hyg_fixture/`
    (four never-compiled fixture files, one per kind of violation).
  - `tests/CMakeLists.txt`: `test_mock_vectors.cpp` in `mc_mock_tests`; ctest entries
    `MCK-HYG.mock_includes` (real `src/mock`, must print `MCK-HYG: OK`),
    `MCK-HYG.negative_control_exit_status` (`WILL_FAIL` over the fixture dir) and four
    `MCK-HYG.negative_control_*` entries, each with a `PASS_REGULAR_EXPRESSION` naming the
    fixture file and violation, so each rule is proved to bite.
  - `tests/qmake/mc_mock_tests.pro`: `test_mock_vectors.cpp` added.
- Deviations from plan (+ reason): none from the Plan. Choices the spec and Plan leave open,
  made here and to be confirmed by the leader:
  - Request data the mock cannot execute (command other than 0401/1401, subcommand other than
    0000..0003, unknown device code, count 0, request-data length not matching the command's
    layout, bad hex character or a bit nibble/character other than 0/1) is answered with
    `MockOptions::unsupportedQna`, with the request's own route, command and subcommand in the
    error information (zeros for a command that could not be read). A **bit-unit** command on a
    **word** device gets the same answer (word devices have no bit view, T-029 notes).
  - Bytes that cannot start a 3E request are dropped one at a time; a contiguous run of them is
    **one** unanswered log record (`answered = false`, defaults elsewhere), so the log does not
    depend on how the stream was fragmented. A 0x50 (binary) or `"5000"` (ASCII) inside the junk
    starts a frame, as it would for any length-framed stream. Header text with a non-hex
    character is junk too.
  - Precedence inside one request: not executable, then bit-op-on-word-device, then `failRange`,
    then device limit, then response-size. A `failRange` therefore wins over
    `setDeviceLimit`.
  - A read whose response would not fit the u16 response-data-length field (ASCII, > 16383
    words) is answered with `unsupportedQna`; the mock does not otherwise enforce the spec §4.4
    point limits (spec does not ask for it; the client's chunking is asserted through the
    request log in INT-07).
  - ASCII decoding also accepts spaces for the `*` of a device code and for leading zeros of
    the device number (spec §3.2 says the PLC accepts them).
  - No private core header beyond `core/protocol/field_codec.h` is included (`device_encode.h`
    is not needed: devices are decoded from `deviceInfo()`).
- Commands run / outcomes:
  - `. scripts/vsdev.ps1; cmake --build build/cmake-debug; ctest --test-dir build/cmake-debug -L "mock|integration|core_session|core_protocol|core_model|build" --output-on-failure`
    -> build clean (`/W4 /WX`), 13/13 ctest entries passed. `mc_mock_tests`: 34 test cases,
    806 assertions, all passed (of which 21 cases are in `test_mock_vectors.cpp`).
  - By hand: `cmake -D MC_MOCK_DIR=tests/mock/hyg_fixture -P tests/mock/check_mock_includes.cmake`
    prints one `MCK-HYG` line per fixture file (frame_3e.h, command_qna.h, serial_parser.h
    includes; `McProtocol` use) and exits non-zero.
  - Not run (planned for Checkpoint C4): MinGW, qmake, coverage.
- Env notes: none new. `PASS_REGULAR_EXPRESSION` in a `cmake -P` negative control needs the
  regex backslash written `\\.` inside a CMake quoted string.
- Notes for the tester:
  - Vectors skipped on purpose in MCK-03: `response-error` records whose `error:` is
    `FrameMismatch` / `LengthMismatch` (malformed responses for the client's parser) and `3E-11`
    (end code with **no** error information; the mock always sends it). MCK-03 asserts that
    exactly two vectors are reproduced (V-3E-B-10, V-3E-A-10). `v1.1`/`v2` vectors (0403 wrapped
    in 3E, 4E) are skipped like `mc_core_protocol_tests` does.
  - MCK-09 (0403 / 1402 answered `unsupportedQna`) is T-031's; T-030 only pins the malformed /
    unsupported paths that the decoder needs.
  - The 3E-12 / 3E-13 (route) vectors have no response vector; MCK-07 derives the expected
    response from the same request with the default route and the route bytes patched in.
  - MCK-HYG: the fixture files live under `tests/mock/hyg_fixture/` and are not part of any
    target; do not add them to a build.
