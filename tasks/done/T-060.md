## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** the tool runs a plan for real: every step kind executes, expectations are
  judged, faults are recovered, and a complete capture set is written.
- **Approach:**
  - `runner.h/.cpp`: `write`/`read` through `McDevice::submit`; `poll` subscribes, runs N
    rounds, applies the step's ad-hoc writes between rounds, records every frame and event;
    `mutate` encodes with `McProtocol`, applies `setByte`/`setNibble`/`append`/`truncate`/
    `replaceSum`, sends on the recording transport; `raw` sends the literal frame; each
    outcome judged against its expectation (`ok`, values, `plcError`, `timeout`,
    `noResponse`, `notSent`, `record`). `bench` steps are executed in T-062 (here they may
    be skipped with a "bench: T-062" note).
  - On `LinkFault`: reconnect (`connectToPlc()`), record the recovery, continue with the
    next step; the faulted step keeps its outcome.
  - Console summary at the end: passed, failed, diverged, not supported, skipped.
  - A small test plan for the end-to-end tests in `tests/hil/` (not the catalogue plans —
    those are T-063), covering every implemented step kind and at least one fault/recovery.
  - The end-to-end tests start `examples/virtual_plc` as a `QProcess` (path from CMake,
    like the existing device tests do for their helpers) and write into a folder under the
    build tree (D3, D5).
- **Files expected to change:** `tools/hil_capture/runner.h/.cpp`, `main.cpp`, the test
  plan and test source, CMake + qmake lists.
- **Acceptance criteria:**
  1. HIL-04 (capture part): a 3E Binary example-style profile against `virtual_plc` over
     loopback TCP writes a full capture set (`run.meta`, `steps.vec`, `session.vec`,
     `bench.csv` header) in which every step of the test plan has its records and outcome;
     the replay half of HIL-04 is added in T-061.
  2. Serial: the same flow with a 3C profile against `virtual_plc --serial` over
     `COM54,COM55` writes a full capture set; the test QSKIPs without
     `MC_TEST_SERIAL_PAIR` and its ctest entry holds `RESOURCE_LOCK mc_serial_pair`.
  3. A fault in the middle of a run (e.g. `virtual_plc` killed and restarted, or a
     `mutate` that the mock answers with silence) is recorded, the tool reconnects and the
     following steps run.
  4. Manual: `hil_capture --dry-run` then a real run against `virtual_plc`, outputs pasted
     (shortened) into Dev notes.
- **Gate 1 approval:** 2026-10-02 — leader, under the owner's delegation extended to Phase 7
  (`rules.md`). Common rules and decisions D1–D5: `tasks/active/T-057.md`.

  - A serial `recover: "eot"` writes EOT (`04`, or `04 0D 0A` in format 4) in raw mode and waits twice the flush time; `reconnect` disconnects and reconnects; `none` leaves the link as it is (a late answer then faults the idle `Session`, which the tool reconnects).
  - The operator prompt of a poll action blocks the event loop while it waits for Enter (documented in `runner.h`); faults that happen meanwhile are seen afterwards.
  - `bench` steps are skipped with "skipped: bench: T-062" (plan allows it).

- **Rework after leader decisions** (decision 8, the poll operator prompt):
  - `Runner::askOperator()` (`runner.cpp`) reads the operator's line on a `std::thread` and posts the answer back to the GUI thread with `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`; the poll loop keeps spinning the event loop (`waitUntil`) until the answer arrives, so the `Session`, its deadlines, the heartbeat and the recording continue while the prompt is open. The thread is joined before the step goes on; the stream is touched by that thread only meanwhile.
  - Test `HIL_04_roundsAndDeadlinesKeepRunningWhileAPromptIsOpen`: a blocking input device (`GatedInput`, its read waits on a semaphore) is released by a timer after 1 s; the poll with a 20 ms cycle must show >= 25 `cycleDone` events in `session.vec` and no gap between two of them of 300 ms or more (a blocked loop leaves a gap of about a second). The older `HIL_04_aPollPromptWaitsForTheOperator` (answer already available) still passes.
  - `runner.h` no longer says the prompt blocks the event loop. The Dev-notes statement "The operator prompt of a poll action blocks the event loop" above is superseded.
