# T-066: X/Y octal numbering for FX CPUs

- **Created:** 2026-10-03  ·  **Plan ref:** — (owner decision 2026-10-03, before Phase 8 and the bench)
- **Class:** `full` → tester: yes · reviewer: yes

## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** the library can address FX3/FX5 X and Y the way their manuals number them (octal),
  on every frame family, without changing anything for Q/L/iQ-R users.
- **Owner quote:** "hãy thêm tùy chọn vào thư viện và implement trước." FX3 and FX5 number X/Y
  in octal and the PLC does not convert (owner checked the vendor manuals).
- **Binding design:** `docs/spec/SPEC-core-model.md`, "X/Y numbering for FX CPUs" (amended
  2026-10-03): `enum class XyNumbering { Hex, Octal }`; `FrameConfig::xyNotation` (text) and
  `FrameConfig::xyAsciiDigits` (ASCII frame digits), both default `Hex`; `Device` holds the point
  index; Binary frames always carry the index.
- **Approach (by layer):**
  1. **core-model:** the enum and the two fields (`frame_config.h`), `parseDevice(text, XyNumbering)`
     and `formatDevice(d, out, capacity, XyNumbering)` overloads (`device.h`); the existing
     functions behave exactly as before. `validate()` uses the digit count actually written.
     JSON-free. Doc comments per the style rule.
  2. **core-protocol:** ASCII device encoding and response/request parsing of X/Y numbers honour
     `xyAsciiDigits` for 3E/1E ASCII, 3C/4C, 1C (find the one place device numbers are written as
     ASCII digits; no per-frame copies). Binary unchanged.
  3. **mock-plc:** the server decodes and answers X/Y with the same `xyAsciiDigits` (its own decoder,
     MCK-HYG independence rule — do not call the codec).
  4. **qt-device:** `McDeviceConfig` JSON gains both fields (spellings `"Hex"`, `"Octal"`; missing =
     `Hex`), and text device fields in the config (e.g. the heartbeat device) are parsed with
     `xyNotation`. `SPEC-qt-device.md` JSON table gets the two rows (leader amends the spec text with
     your exact key names; propose them in Dev notes).
  5. **tools/hil_capture:** profile scratch ranges, `deviceEnd`, plan device references and
     `run.meta` use the profile's `xyNotation` for X/Y; the example FX profiles set
     `xyNotation: Octal` and the right `xyAsciiDigits` per the spec table.
  6. **examples:** `virtual_plc` and `qt_console_poller` device arguments (`--set`, `--sub`,
     `--wiggle`) are parsed with the configured notation; a flag (e.g. `--xy octal|hex` and
     `--xy-ascii octal|hex`) selects it. Keep current behaviour by default.
- **Tests (hand literals from the manuals, not from the code):**
  - core-model: `parseDevice("X10", Octal)` → index 8; `"X377"` → 255; `"X8"`/`"X19"` rejected in
    Octal; `formatDevice` round trips; `Hex` overloads unchanged; non-X/Y symbols unaffected.
  - core-protocol: 1E Binary read `X10` (octal) carries `08 00 00 00` + code (ENET-ADP table:
    X000–X377 ↔ 0000–00FFH); 1E ASCII with Hex digits carries `...00000008`; 1C with Octal digits
    carries `X0010` for index 8 and `X0377` for 255; 3C/3E ASCII with Octal digits likewise; Binary
    3E unchanged; `validate()` field width with octal digits.
  - mock: the same requests are decoded and answered correctly; a 1C octal-digit request with an
    `8`/`9` digit is rejected like any malformed number.
  - device/tools: JSON round trip of both fields; a profile with `xyNotation: Octal` resolves
    `Y@s` / scratch `Y0-Y17` correctly; the gate checks X/Y ranges in indices.
  - Golden vectors: no Appendix A vector changes (they are Q-style); new FX vectors go in a new
    `.vec` file tagged with their manual source, VEC-02-style length check where a byte count is
    known.
- **Files expected to change:** `include/mc/core/frame_config.h`, `include/mc/core/device.h`,
  `src/core/model/*`, `src/core/protocol/*` (device encode/decode), `src/mock/*`,
  `src/device/mc_device_config.cpp`, `tools/hil_capture/*` (profile, resolve), example profiles,
  `examples/*/main.cpp`, tests in every layer, `tests/vectors/` (new FX file), `CHANGELOG.md`.
  This touches several layers; keep each change minimal and local.
- **Acceptance criteria:**
  1. With default settings every existing test, vector and replay fixture passes unchanged.
  2. All tests listed above pass on MSVC and MinGW; coverage bars kept; qmake case lists equal.
  3. Public API additions only as in the spec (enum, two fields, two overloads, JSON keys); no
     other public declaration change.
  4. Mutants: Octal parsed as Hex; ASCII digits ignore the setting; mock ignores the setting;
     Binary frames affected by the setting — each fails a test.
- **Gate 1 approval:** 2026-10-03 — leader; the feature is the owner's decision. Gate 2: owner

## Dev notes  *(developer writes)*

**Map of device numbers before the change (one implementation per concern).** Text is parsed and
formatted in one place per layer; ASCII digits are written in one place (core) and read in one
place per mock decoder.
- core-model: `src/core/model/device_parse.cpp` (`parseDevice`/`formatDevice`, text);
  `device_table.cpp` (radix per symbol); `validate.cpp` (`digitLimit`/`deviceNumberLimit`: field
  width in digits). `chunk.cpp`, `limits_table.cpp`, `session/*` only see indices.
- core-protocol: `src/core/protocol/device_encode.cpp`: `putFixedWidthNumber` writes the QnA ASCII
  digits (6 or 8) and the 1C digits (4/6, T/C 3/5); `AsciiCodec::putU32` writes the 1E ASCII 8
  hex digits; Binary writes the number as LE bytes. Called only from `command_qna.cpp`,
  `command_a1e.cpp`, `command_a1c.cpp`. No response carries a device number, so no parser reads one.
- mock: its own decoder (MCK-HYG): `request_decode_ethernet.cpp` (`digitValue`,
  `parseDeviceNumber`, `decodeQnaAsciiDevice` for 3E and 3C, `decodeE1Device`),
  `request_decode_serial.cpp` (`decodeDevice1c`). The mock never writes a device number.
- device: `mc_device_config.cpp` (heartbeat device text in `fromJson`/`toJson`, subscription text in
  `validate()`), `mc_device.cpp` (`parseHead` for every text argument and the construction-time
  subscriptions).
- tools/hil_capture: `profile.cpp` (scratch, `deviceEnd`, `specialBit/Word`, `scanTimeDevice`;
  `parseDeviceNumber`/`formatDeviceNumber`/`deviceText`, which had a second copy of the radix rules),
  `plan.cpp` (`parseDeviceRef` literals), `resolve.cpp` (`resolveRef`, step descriptions),
  `safety_gate.cpp`, `dry_run.cpp`, `capture_writer.cpp` (`run.meta`, session events), `runner.cpp`.
- examples: `virtual_plc` (`--set`, `--wiggle`, log lines), `qt_console_poller` (`--sub`, output).
  `session_loop` is Q-style, untouched. `tests/hil/replay/replay_util.cpp` has its own hex-only
  `deviceText` (see "For the leader").

**Design as built.** `XyNumbering` and the two `FrameConfig` fields in `frame_config.h`;
`parseDevice(text, xy)` / `formatDevice(d, out, capacity, xy)` overloads, the old functions call them
with `Hex`. One internal helper `detail::numberBase(info, xy)` in `src/core/model/validate_internal.h`
(8 for X/Y under Octal, else the table radix) is used by parse/format (`xyNotation`), by `validate()`
and by `device_encode.cpp` (`xyAsciiDigits`). `validate()` counts the digits written: 1C ACPU X
index 4095 is the last under Octal, 3E ASCII Q/L 262143, iQ-R and 1E ASCII 16777215; Binary frames are
never narrowed. `qnaDevice`, `e1Device`, `c1Device` and the three request-data encoders take a trailing
`XyNumbering` (default `Hex`); `frame_3e/1e/serial.cpp` pass `cfg.xyAsciiDigits`. The mock threads
`cfg.xyAsciiDigits` into its own decoders and has its own `asciiNumberBase`.

**Proposed JSON keys for `SPEC-qt-device.md`** (rows in the `McDeviceConfig` JSON table, inside the
`frame` object, after `readRetries`): `frame.xyNotation` and `frame.xyAsciiDigits`, enum strings
`"Hex"` / `"Octal"` (exact case; anything else fails with that key as `where`), missing key = `"Hex"`.
Text devices in the config (`session.heartbeat.device`, `subscriptions[].device`) are read and
written in `frame.xyNotation`; `McDevice` text arguments (`subscribe`, `readWords`, ...) likewise.
