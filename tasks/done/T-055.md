
You should see `virtual_plc listening on COM52 9600 7E1 (3C format 4)`, then one line `wiggle D105 = N` every second. (There is no "client connected" line on a COM port.)

Terminal 2 (the poller, the other end), started after terminal 1 says "listening":

```powershell
cd C:\DGB\Project\mc_protocol
$env:PATH = "C:\Qt\6.11.1\msvc2022_64\bin;$env:PATH"
build\cmake-debug\examples\qt_console_poller.exe --frame 3C --format 4 --serial COM53 --sub D100:8 --sub M0:16
```

You should see: `link: Connecting (Requested) COM53 9600 7E1`, `link: Connected (Requested) COM53 9600 7E1`, the round-1 snapshots (`snapshot M, round 1` with two rows of eight zeros, `snapshot D, round 1` with `D100 :  1234     0     0     0     0     1     0     0` or similar), then about once a second `changed D105: 1 -> 2 (round 8)`, `2 -> 3 (round 15)`, and so on (a round is 100 ms; with the serial line a round takes about 140 ms, so roughly 7 rounds per second). If terminal 2 starts more than a second after terminal 1, D105 is already 1 or higher in the round-1 snapshot.

Scripted variant that ends by itself: add `--rounds 35` to the poller; it prints `done after 35 rounds` and `link: Disconnected (Requested) ` (trailing space) and exits with code 0 (`echo $LASTEXITCODE` right after it returns; 1 after a link fault or a failed open, 2 for a bad argument). Stop: Ctrl+C in terminal 2, then in terminal 1.

Optional checks: other frames over the same pair, `--frame 1C --format 1` on both sides (1C uses the ACPU command set); `--baud 19200` on both sides; terminal 1 stopped with Ctrl+C while the poller runs: the poller does not see a closed peer (a serial line has none), it times out and ends with `link fault: timeout (no response within the timeout)` and exit code 1; poller without terminal 1 (checked): `chunk D100 x8 failed: no response within the timeout` in the round-1 snapshot, then `link fault: timeout ...`, `link: Faulted (Fault) ...`, exit 1. Checked by me: `--frame 1C --format 1 --baud 19200` on both sides works (`D100 : 77 ...`, exit 0 with `--rounds 5`). A wrong line setting between the two ends also ends in timeouts, not in a clear error (spec, `SerialSettings`).

## Review verdict  *(reviewer writes — skipped only if Class says so)*

- Findings (severity · file:line · what/why):
  1. **should-fix (decision for leader/owner, no code change needed to pass)** · `src/core/session/session_rx.cpp:77-97` with `src/core/protocol/frame_serial.cpp:163-187` · Open question A is sharper than T-051's note and the leader's decision 4 say. The overflow bound is `maxResponseSize()` applied to the whole receive buffer, junk included. For a poll or ad-hoc **read** the data frame is the largest possible response and is exactly the size of every successful response (3C F1 D100x3: 26 bytes = V-3C1-02; the test at `tests/core/session/test_session_fault.cpp:1301-1318` pins "26 noise bytes ok, 27th overflows"). So not only "a maximum-size response preceded by junk" but **every successful read response preceded (or followed in the same call) by even one stray byte** takes the overflow path: EOT, flush, resend, one consecutive link error. Writes have 2-4 bytes of slack (NAK is larger than ACK). Consequence: the parser's "skip until STX/ENQ" (spec 6.3) and `Corruption::JunkPrefix` ("serial: must be skipped", SPEC-mock-plc) never apply to reads end to end; the retry hides it, and no test (session or INT) pins junk plus a valid frame either way. I judge the literal reading defensible (the spec says "sized to the largest possible response" and the fault table is Ask-first), so this does not block. Do: record it in `decisions.md` and the owner's Checkpoint E report with this exact consequence, and ask the owner whether the bound should count only bytes from the start byte (or add a small junk allowance); if the literal reading stays, add one test that pins "1 junk byte + valid read response = overflow path" so a later change is a conscious one.
