  buffer, `Parser` driving, decode into the store, `ValuesChanged` per response

  `CycleDone`.

  exactly; `src/core/session/session_rx.cpp` drives the `std::optional<Parser>`

  - `tests/core/session/harness.h` / `harness.cpp` — **not in this task's file list**:

  - `src/CMakeLists.txt` / `mc_core.pri` — added `session_rx.cpp`.

- Deviations from plan (+ reason):
  - **Touched `include/mc/core/session.h`** (not in this task's file list): `Output::payload`/
    `Output::changes` are raw pointers that must stay valid until the next input call (`Output`'s
    own doc), so the memory `ValueStore::apply()` decodes into and writes `Change`s into cannot
    be a local variable in `completeCurrentChunk()` — it must outlive that single function call.
    Added it as two `Session` private members, sized to the current plan's own
    `maxPayloadSize()`/`maxChunkPoints()` in `encodeAllChunks()` (same place `m_encodedChunks`
    itself is already resized). This is the same category of "the spec's own contract requires
    persistent storage this task's file list has nowhere else to put" as T-020/T-021/T-022's own
    `poll_plan.h` touches — `session.h` ends up being the one header edited across two
    consecutive tasks (T-022, T-023) rather than only T-022, which is worth the leader/owner
    knowing explicitly rather than discovering at the checkpoint.
  - **Touched `tests/core/session/harness.h`/`harness.cpp`**: your own message for this task said
    to make sure the harness "makes a poll timeline easy to read" and that you report its style
    to the owner — read as an invitation to improve the harness, not just use it as-is. Added
    `OutputRecorder::back()` (used by nothing yet, cheap, obviously useful for a later "last
    output was X" style assertion) and `RecordingLogSink` (needed for SES-26's "logged at Warn"
    half; the harness had no way to observe a `LogSink` call before this task).
  - **SES-02..05 are one test, not four.** The spec's own "Publishing values" section already
    works through exactly this scenario (`M0x128`, `D100x64`, `D2000x64`, third chunk NAKs in
    round 1) as its worked example, covering rounds 1 and 2, every rule (S1-S5), and — because
    the third (`D2000`) chunk fails in round 1 and succeeds in round 2 — SES-05 ("chunk failed in
    round 1, succeeds in round 2 → silent baseline") for free. Reproducing it verbatim, one
    `bytesIn()`/`tick()` per row of the spec's own table with a comment quoting that exact row,
    seemed the most direct way to satisfy "the timeline of 'Publishing values' is reproduced
    exactly" (this task's own acceptance criterion 1) and the clearest for Checkpoint C1 (a
    reader can put the spec's table and this test side by side, row for row). SES-06 needed its
    own separate, smaller test (4 rounds, `Ok → Ok(changed) → Failed → Ok(changed again)` on one
    subscription) since it is not part of that same worked example.
  - **A real bug, found by inspection, not a test failure — flagging prominently for T-024**:
    `Output::chunks`/`Output::changes` (`Snapshot`/`ValuesChanged`) point directly into `m_plan`'s
    own storage and `m_changeBuf` respectively; both are valid "until the next input call"
    (`Output`'s own contract). But if a round ends *with a pending re-plan* (`subscribe()`/
    `unsubscribe()` was called mid-round or mid-previous-round) *and* the next round is due
    immediately (`cycleIntervalMs` low enough, or 0) — the same back-to-back path SES-07's own
    interval-0/130ms `SUBCASE`s exercise — `dispatch()` calls `startRound()` → `applyRePlan()`
    **within the same input call** that just pushed that round's own `Snapshot`(s) into the
    output ring. `applyRePlan()` replaces `m_plan` (`m_plan = std::move(newPlan)`), destroying the
    old `ReadPlan`'s backing storage — so a `Snapshot` pushed earlier in that *same* call now
    holds a dangling `chunks` pointer, before the caller has even had a chance to drain it. None
    of my own tests reach this (no test in this file calls `subscribe()`/`unsubscribe()` after
    `linkUp()`), so it is unverified-by-test, not a failing assertion — but it is real, walked
    through by hand against the actual code, not a hunch. T-020's Dev notes already flagged
    general "re-plan safety while a round is genuinely mid-flight" as T-024 territory; this is a
    concrete, specific instance of that risk, worth T-024 reading before it writes SES-22.
