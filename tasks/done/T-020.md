- Deviations from plan (+ reason):
  - **PLN-10 is not in this task's `test_range_set.cpp`.** The spec's Testing Strategy table
    describes PLN-10 as "Re-plan carries value and state for surviving points; new points
    `NoValue`; dropped points `NotSubscribed`" — `NoValue`/`NotSubscribed` are
    `PointState` enumerators (`value_store.h`), and the carry-over behaviour it describes is
    `ValueStore::rebuild()`'s own contract (spec's `value_store.h` sketch: "Re-shapes the store
    for a new `RangeSet`: points covered before and after keep value and state; new points start
    `NoValue`; dropped points disappear"). `RangeSet`/`ReadPlan` (this task's only files) have no
    notion of a point's value at all, and `value_store.h`/`ValueStore` is T-021's scope, not
    named in this task's file list. I flag this rather than choosing silently (role contract);
    since I continue as the same developer into T-021 next in this phase, I will add the actual
    PLN-10 test case there, against `ValueStore::rebuild()`, in `test_value_store.cpp` — the
    phase checkpoint's `ctest -L core_session` (T-028) then covers it together with everything
    else, per phase-batched verification. This is a request for the leader to confirm that
    placement is acceptable, not a blocker: PLN-01, 02, 04-09 and acceptance criterion 2 (a
    failing `build()` keeps the previous plan) are all implemented and tested now.
  - `ReadPlan::build()` slices any merged interval wider than 65535 read units into several
    `Request`s before calling `mc::chunk()` on each (`Request::count` is `uint16_t`, but
    `RangeSet::add()`'s own `count` is `uint32_t`). Not called out by the spec's algorithm
    sketch; necessary for correctness on a subscription wider than 65535 points, which
    `RangeSet::add()` otherwise legally allows. No currently-listed test reaches this path (the
    widest PLN case is 8000 points); recorded here as an implementation note, not tested
    separately, since it does not change behaviour for anything the acceptance criteria name.
  - `autoGap()` cannot use `McProtocol::payloadSize()` for the marginal per-unit wire cost:
    that function returns the library's own *normalized* payload size (always 2 bytes/word,
    1 byte/bit `BytePerPoint`), not the frame's *wire* size (4 hex chars/word for ASCII, etc.) —
    conflating the two was my first draft and it failed PLN-03 for 3E ASCII (132 instead of 16)
    before I caught it locally. The implementation instead differences
    `McProtocol::maxResponseSize()` at two large counts (100 and 101 read units) to isolate the
    marginal wire cost, then extrapolates back down to 1 unit; both are public `McProtocol`
    calls, no `mc::detail` access needed. Documented in the function's own comments.

- Env notes (new facts about the build environment, for build-env.md):
  - The qmake "stale sub-Makefile" gotcha (build-env.md already documents the general rule) has
    a nested-subdirs wrinkle worth adding: `mc_protocol.pro` → `tests/qmake/tests.pro` →
    per-binary `.pro` is *two* levels of `TEMPLATE = subdirs`, and the intermediate level's own
    sub-Makefile (`tests/qmake/Makefile.tests`, generated from `tests.pro`'s own project name,
    not the parent's `SUBDIRS` variable name `tests_qmake`) is *not* regenerated merely by
    rerunning `qmake mc_protocol.pro` at the top — that command only touches the top-level
    `Makefile`; the nested Makefiles are (re)generated lazily, only when `nmake` actually
    recurses into that subdir's target (`if not exist Makefile.tests qmake ...` is a rule
    inside the generated Makefile, not something a bare `qmake` invocation runs). After adding a
    new binary to `tests.pro`'s `SUBDIRS`, the fix is: delete
    `build/qmake-*/tests/qmake/Makefile.tests*`, then run `nmake` (not just `qmake`) from
    `build/qmake-*` — the missing sub-Makefile is regenerated automatically as part of that
    build.
