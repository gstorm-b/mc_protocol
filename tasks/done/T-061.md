## Plan  *(leader writes; Gate 1 approves)*

- **Goal:** a hardware-free doctest binary that replays capture folders against the encoder,
  the parser, the mock and the `Session` on every build.
- **Approach** (spec "Replay tests"):
  - `tests/hil/test_replay.cpp`, binary `mc_replay_tests`, label `replay`, std-only (links
    `mc::core` and `mc::mock`, never Qt; built with tests + mock).
  - Walks `<root>/*/` where `<root>` defaults to `tests/vectors/captured/` (absent or empty →
    passes with a "no captures" note). A root override (command-line option and/or env var,
    your choice, documented) lets HIL-04 point it at a capture made under the build tree
    (D3).
  - RPL-01 re-encode from metadata with the `FrameConfig` rebuilt from `run.meta`; RPL-02
    parse to the recorded outcome and values; RPL-03 mock conformance (seed unwritten
    memory from captured reads, then responses byte-equal); RPL-04 session replay on a fake
    clock (same tx frames in order, same events); RPL-05 capture sanity (write followed by a
    matching read-back; `GV` steps equal the Appendix A vector they mirror); RPL-06 every
    `divergences.txt` id has an entry in `docs/hil/FINDINGS.md`. Steps listed in
    `divergences.txt` report `known-divergence` and do not fail.
  - Each failure names the profile and the step (user story "names the profile and the
    step").
  - Fixtures (D3): a small capture set made by the tool against `virtual_plc`, committed
    under `tests/hil/fixtures/<id>/` with the "virtual_plc fixture, not hardware" note, so
    the RPL checks run on every build; negative tests copy it to a scratch folder under the
    build tree and change one byte / one value / one event to prove each RPL check fails.
  - HIL-04 replay half: the hil_tool end-to-end test (T-060) runs `mc_replay_tests` on the
    capture it just wrote and expects success.
- **Files expected to change:** `tests/hil/test_replay.cpp`, `tests/hil/fixtures/…`,
  `tests/CMakeLists.txt`, its qmake twin, the HIL-04 test (small addition).
- **Build folder:** you work in parallel with the tool developer. Build in your own folder
  `build/cmake-debug-dev2` (MSVC Ninja, configured like `build/cmake-debug`), never in
  `build/cmake-debug`.
- **Acceptance criteria:**
  1. RPL-01…06 pass on the fixture set; each has a negative test that fails it with the
     profile and step in the message.
  2. With an empty or absent root the binary passes and prints the "no captures" note.
  3. HIL-04 complete: the end-to-end capture from T-060 replays green.
  4. `ctest -L replay` on MSVC and MinGW; the binary links no Qt (BLD-style check or
     `dumpbin /dependents` / `objdump -p` recorded).
- **Gate 1 approval:** 2026-10-02 — leader, under the owner's delegation extended to Phase 7
  (`rules.md`). Common rules and decisions D1–D5: `tasks/active/T-057.md`.

- Deviations from the Plan (+ reason):
  - **HIL-04 replay half is not wired** (leader instruction). The hook should run `$<TARGET_FILE:mc_replay_tests>` (a compile definition to add to `mc_hil_tool_tests`, plus `add_dependencies`) with the arguments `--replay-root=<output root>/captured` and `-tc="RPL-sweep: every*"` (only the sweep case, not the fixtures and negatives again). Exit code 0 = green; failing lines name check, profile and step. `<output root>/captured` is the folder that holds `e2e-3e-bin/` (the tool writes `<output-root>/<profile id>/`).
  - **Format gaps the replay works around** (the capture format is T-059/T-060, not changed): (1) the poll inputs (subscriptions, heartbeat, ad-hoc writes, when) are not in `session.vec`; RPL-04 rebuilds them from the transcript: heartbeat = the first frame is a one-bit write; subscriptions = the segments of the snapshot events, a change first visible in round N was made during round N-1; ad-hoc write = a written frame that is not the heartbeat, decoded with a `MockPlc` and submitted at its own time, or before the response that released it when it followed that response by under 100 us. The rules are in the header of `replay_session.cpp`. Writing the inputs into `session.vec` (T-062 owner) would make this exact. (2) `steps.vec` has no marker for a step that ran with a `frameOverride`: RPL-01 would fail on such an api record. The loader honours an optional record key `override: <text>` (RPL-01 skips the record, with a note); the writer should emit it when a step runs with another FrameConfig (T-063 plans G4-03/04, G7-03, G9-05). (3) The `divergences.txt` format was unspecified: one line per tagged step, `<step id> <FINDINGS id>`, `#` comments; RPL-06 needs `### <FINDINGS id>` as a heading in `docs/hil/FINDINGS.md` and the step to exist in the capture. A step id matches its record ids (`G1-04`, `G1-04.2`, `G1-04+2`) and the poll step.
  - **RPL-01 data of a write** comes from decoding the captured request with a `MockPlc` (the metadata has no values), so a changed data byte is caught by RPL-05 / RPL-03, not RPL-01. **RPL-03 seeding**: a point is seeded from the captured read until the replay has written it; points written by a poll step are seeded every time (the timing of a poll against the steps is not recorded). After a `recovery.<n>` of a TCP capture the mock is replaced by a fresh one and memory is not assumed (virtual_plc gives each connection a fresh mock; a note is printed). For mutate/raw records the request bytes are fed to the mock as they are.
  - RPL-05 GV rule: the request must equal the mirrored Appendix A vector with the same op, device and count; the response must equal it when the parsed payload equals the vector's (the "default values" case). A GV step whose records match no mirrored vector fails. The `mirrors` key is only read on steps whose id starts with `GV`.
  - A cycle's `durationMs` may differ by up to 2 ms from the recorded one (stamps and Session clock have different origins); tx frames and events are compared as two separate lists.
