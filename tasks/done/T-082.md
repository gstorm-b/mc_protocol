  The old driver closed with `disconnectFromHost()` (FIN) and set no socket options. v0.1.0 always closes with `abort()` (RST) and always sets `LowDelayOption` and `KeepAliveOption` (`src/device/tcp_transport.cpp`, `onConnected`, `finishClosed`).
- **Goal:**
  - `TcpSettings` gains `lowDelay`, `keepAlive` and `closeGraceMs`.
  - `TcpTransport::close()` can end a connected socket gracefully, while keeping the `Transport::close()` contract (`Closed` at once, no signal, `open()` right after works).
  - `virtual_plc` can imitate a PLC that serves a new connection late, so the app team can try their reconnect handling without hardware.
  - Defaults keep v0.1.0 behaviour.
- **Approach:**
  1. **`include/mc/device/tcp_transport.h`.**
     - Add the three fields with the spec's defaults and Doxygen.
     - Update the class and `close()` / destructor Doxygen: options per settings; graceful close; the destructor aborts a close in progress.
  2. **`src/device/tcp_transport.cpp`.**
     - **`onConnected`:** set each option only when its flag is true. When false, do not touch the option, so the OS default holds.
     - **`close()` / `finishClosed()`, when `closeGraceMs > 0` and the socket is `ConnectedState`:**
       - **detach** the current socket: disconnect all its connections to `this`, keep it as a child, and give it a single-shot `QTimer` child (or a `QTimer::singleShot` with the socket as context) that `abort()`s it after `closeGraceMs`;
       - call `disconnectFromHost()` on it (this flushes pending writes, then sends FIN);
       - `deleteLater()` it on `disconnected` or after the abort;
       - **create a fresh `QTcpSocket`** for the transport and connect it as in the constructor (factor the wiring into one function);
       - otherwise (grace 0, or not connected): `abort()` as today.
     - **No signal** from a closing socket may reach the transport's slots. **No `waitFor*`, no nested loop.**
     - **The `write()` failure path and `onError` / `onDisconnected`:** these are losses, not requested closes. Keep `abort()` there; only `close()` is graceful. Say in the Dev notes how you kept the two paths apart.
     - **Destructor:** closing sockets are children and are aborted and deleted with the transport. Make their signals inert first, as the destructor does today.
  3. **JSON.** `src/device/mc_device_config.cpp`:
     - read and write `transport.tcp.lowDelay` (bool), `keepAlive` (bool) and `closeGraceMs` (int);
     - missing keys take the defaults; a wrong type gives the usual error with its path;
     - `validate()` rejects `closeGraceMs` outside 0 … 60000 with path `transport.tcp.closeGraceMs`;
     - QDV-10 cases: round trip, defaults, wrong types, range.
  4. **GUI fields.** `tools/mc_workbench/config_binding.cpp`:
     - `transport/tcp/lowDelay` (Bool, "No Nagle delay on requests");
     - `transport/tcp/keepAlive` (Bool, "TCP keep-alive, OS timing");
     - `transport/tcp/closeGraceMs` (Int, 0 … 60000, "Close: 0 = reset at once; > 0 = FIN, reset after this many ms");
     - GUI-06 must pass. Check whether the device tab hides TCP fields when the transport is Serial and follow that pattern.
  5. **Tests** in `tests/device/tst_tcp_transport.cpp`:
     - QDV-12 is extended as the spec row says. Read back with `socketOption()` through the test's existing access path; read how QDV-12 does it today.
     - QDV-19 is new, exactly as the spec row says. For "bytes reach the server", write and then `close()` in the same event-loop turn, so the bytes are still in Qt's write buffer. With grace 0 the same sequence must deliver nothing; if that is not deterministic on Windows, say so and assert only the graceful side. For "never closes its side", the server keeps its socket open and does not read EOF-driven closes. Count the transport's `QTcpSocket` children to see the lingering socket go away.
     - No fixed sleeps without a bound; use `QTRY_*` with margins (see lessons [T-077], [T-071]).
  6. **`examples/virtual_plc/main.cpp`.** Add `--hold-first-ms N`: on each accepted TCP connection, the first request is answered after N ms (later requests queue behind it). It works like T-081's `MockPlcServer::holdFirstRequest`, but it is the example's own code (examples do not link test code). TCP only; with `--serial`, refuse it with a clear message. Help text: "Answer each connection's first request after N ms (imitates a PLC that serves a new connection late)." Add a smoke test only if the examples already have one that runs `virtual_plc` with options; otherwise give a manual check in the Dev notes:
     - run `virtual_plc` with `--hold-first-ms 3000`;
     - poll it with `qt_console_poller`, or GUI `MockRunner` if `qt_console_poller` cannot set the timeout;
     - expect a timeout with the default settings, and success with `firstResponseTimeoutMs` 5000 set through its config.

     If `qt_console_poller` cannot set the session config, add **nothing** to it; report it.
  7. **No change** to `Transport` (the abstract class), `McDevice`'s state machine, or `SerialTransport`.

## Dev notes  *(developer writes)*

- Files changed:
  - `include/mc/device/tcp_transport.h` — `TcpSettings` gains `lowDelay`, `keepAlive`, `closeGraceMs` (spec defaults, Doxygen); class/`close()`/destructor docs updated; private `createSocket()`, `closeGracefully()`; `m_socket` is now assigned in `createSocket()`.
  - `src/device/tcp_transport.cpp` — `onConnected` sets each option only when its flag is true; `createSocket()` holds the signal wiring (used by the constructor and after a graceful close); `close()` takes the graceful path; `closeGracefully()` detaches the old socket, creates a fresh one, arms the grace timer and calls `disconnectFromHost()`.
  - `src/device/mc_device_config.cpp` — reads and writes `transport.tcp.lowDelay/keepAlive/closeGraceMs`; `validate()` rejects `closeGraceMs` outside 0..60000 (path `transport.tcp.closeGraceMs`; checked in the Tcp branch, as host and port are).
  - `tools/mc_workbench/config_binding.cpp` — three fields `transport/tcp/lowDelay`, `keepAlive` (Bool), `closeGraceMs` (Int 0..60000) with the Plan's tool tips. No change needed for hiding TCP fields on Serial: the binding already hides the whole `transport/tcp` group by kind (lines ~464).
  - `tests/device/tst_tcp_transport.cpp` — QDV-12: `switchedOffOptionsAreNotSetByTheTransport`, `eachOptionIsSwitchedOnItsOwn` (the original default-case test is unchanged). QDV-19: graceful close delivers bytes then EOF; grace 0 discards the bytes; stuck peer sees the closing socket aborted after the grace time and `open()` right after `close()` makes a second connection; destroying mid-grace deletes the closing socket at once (QPointer); close while connecting stays an abort. Helpers `socketsOf()`, `fillUntilTheSocketCannotFlush()`.
  - `tests/device/tst_config_json.cpp` — QDV-10: `kTcpKeys`, full round trip values, defaults, wrong types (bool as number, strings, fraction), `closeGraceMs` range -1/0/60000/60001. One existing case edited, see Deviations.
  - `tests/gui/tst_gui_workspace.cpp` — GUI-08 only: the "unknown key" fixture used `tcp.keepAlive`; renamed to `tcp.tcpNoDelayHint`. See Deviations.
  - `examples/virtual_plc/main.cpp` — `--hold-first-ms N` (TCP only; refused with `--serial`, exit 2; negative or non-number refused). Per connection the answers wait in a queue until a single-shot timer (started at the first request) ends the hold; later answers queue behind it.
- How the two close paths stay apart: `close()` is the only place that calls `closeGracefully()` (condition: `closeGraceMs > 0`, state `Open`, socket `ConnectedState`). `finishClosed()` (used by `write()` failure, `onError`, `onDisconnected`, connect timeout, and `close()` in every other case) is unchanged and still `abort()`s. A socket that is still connecting is always aborted.
- Deviations from plan (+ reason):
  - Existing tests edited (not only added to): `tst_config_json.cpp` `QDV_10_unknownKeysAreIgnored` and `tst_gui_workspace.cpp` `GUI_08_unknownKeysAreReportedWithTheirPath` used `keepAlive` as an example of an unknown TCP key; it is a real key now, so both failed (`expected a boolean`). I changed only that key name (to `unknownTcpKey` / `tcpNoDelayHint`). `tst_gui_workspace.cpp` is not in the Plan's file list.
  - The QDV-19 "server never closes its side" case is built on Qt behaviour the Plan did not assume: `QAbstractSocket::disconnectFromHost()` closes the native socket as soon as Qt's write buffer is empty (it does not wait for the peer's FIN; the OS finishes the FIN exchange), so with a quiet peer the closing socket is gone after the flush. The grace timer only matters while bytes stay in Qt's buffer, i.e. when the peer does not take them. The test therefore uses a peer that does not read (read limit of 1 byte) and writes 4 MB chunks until Qt holds 16 MB the kernel refused (Windows loopback takes about 24 MB first; with less backlog it drained within ~100 ms and the test failed on the lower bound). The lower bound (`>= grace - 50 ms`) is the only timing assertion; the upper side uses a `QTRY` timeout of grace + 5 s. Peak memory in this test is about 70 MB.
  - Grace-0 case: deterministic here (Qt flushes on the event loop, not inside `write()`); asserted that the peer receives nothing.
