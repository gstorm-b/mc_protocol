- Deviations from plan (+ reason):
  - **Superseded by the Rework below — kept here only as a record of the original submission.**
    The Approach says "the full table of spec §4.4, random-access rows included (kept for
    v1.1)". I transcribed the random-access rows (0403, 1402) as a **comment block**, not as
    `constexpr` data, for two reasons: (1) several of them are combined constraints across two
    separate counts (`m x12 + n x14 <= 1920`, `m + n <= 192`), not a single point maximum the way
    every other row is — forcing them into `LimitRow`'s `{iqrQl, qna, a}` shape would misrepresent
    them, not just leave them unused; (2) v1's `Op` has no random-access value, so any
    `constexpr`/`static` row data for them would be genuinely unreferenced anywhere in the
    program — under GCC (`-Wall -Wextra`, used at Checkpoint A's MinGW build) an unused
    internal-linkage namespace-scope variable is a real `-Wunused-variable` risk with
    `MC_WARNINGS_AS_ERRORS=ON`, which I could not verify one way or the other on this machine's
    MSVC-only daily loop. The leader's ruling: this conflicted with the approved module spec
    (`docs/spec/SPEC-core-model.md:328`, "the full table including random-access rows is stored
    in `limits_table.cpp` so v1.1 needs no table change" — a comment block still needs a table
    change), which only the owner may amend, so it had to be reworked rather than left as a
    judgment call.
  - Touched `CHANGELOG.md`, not in the Plan's file list — same Definition-of-Done reason recorded
    in T-007/T-008. Still applies after the Rework.

- Rework (leader): the leader asked for the random-access rows to become real `constexpr` data
  after all, kept internal (no public header/symbol), referenced from a real function to avoid
  `-Wunused-variable` under GCC, and tested.
  - `src/core/model/limits_table.h` (new, private): `mc::detail::RandomAccessCommand` (one
    enumerator per command/subcommand: `Read0403Sub0000/0002`,
    `Write1402WordSub0000/0002`, `Write1402BitSub0001/0003`) and
    `mc::detail::RandomAccessLimitRow` (`command`, `family`, `weightM`, `weightN`, `total`). Every
    row reads as one formula, `weightM * m + weightN * n <= total`: the manual mixes a genuinely
    combined two-count constraint (0403, 1402-word) with a plain single-count maximum (1402-bit,
    and 1402-word's odd "A: m ≤ 10" cell, which caps `m` alone with no `n` term at all) — a zero
    weight just drops that term, so one row shape covers both without a shape flag.
  - `src/core/model/limits_table.cpp`: `kRandomAccessLimitTable` (in an anonymous namespace) plus
    `mc::detail::randomAccessLimitRowCount()`/`randomAccessLimitRow(size_t)` (ordinary, non-
    `static` functions defined in the same file, each indexing the array directly — this is what
    makes the array "used" from the compiler's perspective, regardless of whether anything else
    ever calls the accessors; neither accessor is itself `static`/anonymous-namespace, so
    `-Wunused-function` does not apply to them either). No warning was suppressed anywhere.
  - **Row count: 11, not 9.** Re-reading spec §4.4 directly (not my own prior code): 0403 sub0000
    has 2 non-blank cells (IqR_Q_L 192, QnA 96; A is "—"), 0403 sub0002 has 1 (IqR_Q_L 96), 1402
    word sub0000 has 3 (IqR_Q_L ≤1920, QnA ≤960, A "m ≤ 10" = 10), 1402 word sub0002 has 1
    (IqR_Q_L ≤960), 1402 bit sub0001 has 3 (IqR_Q_L 188, QnA 94, A 20), 1402 bit sub0003 has 1
    (IqR_Q_L 94) = 2+1+3+1+3+1 = 11. I could not find a reading of the reference table that gives
    9 non-blank cells; flagging this count mismatch explicitly rather than silently picking a
    subset — if a narrower set was intended (e.g. excluding the two "1402 bit" rows, which are
    plain maxima rather than combined constraints, or excluding the odd "A: m ≤ 10" cell), let me
    know and I will trim `kRandomAccessLimitTable`/LIM-03 accordingly.
  - `tests/core/model/test_limits.cpp`: new `LIM-03` test case, adds
