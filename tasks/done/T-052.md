## Plan  *(leader writes; Gate 1 approves)*

- **Approach:**
  - `src/mock/request_decode_serial.cpp` per the spec's "Serial reception":
    F1/F2/F4 skip until `ENQ`, F3 until `STX` (skipped bytes counted);
    request length computed from the command and point count for F1/F2/F4
    (no terminator before SUM; F4 ends in `CR LF`), F3 reads to `ETX`; SUM
    verified when `cfg.sumCheck` (wrong → NAK / `QNAK` / `NN` with
    `sumError*`); station mismatch → no response; `EOT` (F4: `EOT CR LF`)

    message-wait character accepted and ignored.

- Deviations from plan (+ reason):
  1. Files not in the Plan's list: `src/mock/request_decode_ethernet.cpp` (shared helpers instead of copies, DoD "no duplicated logic"),
     `command_exec.cpp` (listed in the Plan only as "mock_internal.h"/others; needed for `executeSerial`), `tests/mock/serial_frames.h`.
  2. Plan's `corruption.cpp` item "`WrongRoute` on the station/PC field": implemented as station, network and PC on 3C and station and PC on 1C.
  3. MCK-02 skips the 8 vectors with `checkroute: off` / `blockcheck: off`: they are responses whose route or block number differs from the
     request's (for client-side checks), which a PLC that echoes the request cannot produce. Their requests are in MCK-01/05.
  4. `seedFromExpect` of the vector tests now steps 16 points per word on a bit device (1C X40 word vectors).
- Behaviours the spec leaves open (my choices; challenge them):
  1. Skipped serial bytes are not counted anywhere: the spec says "counted" but MockPlc has no accessor for it (public API fixed), so a counter would be dead state. Not in `requests()`.
  2. A F1/F2/F4 request whose layout cannot be computed (unknown command, 4C frame ID "F8", non-hex route/wait, unknown 0401 subcommand, control code inside) is dropped like junk (start byte dropped, scan resumes at the next start byte, no response, no record). F3 frames are always framed by ETX: unknown command or bad data is answered with unsupported*; a bad route (frame ID, non-hex) is junk.
  3. 0403/1402 (3C) and BT/WT/JT/QT (1C) are framed by their n x item layout (spec 4.1.3-4.1.5, 4.3) so they can be answered; answered with unsupportedQna / unsupported1c.
  4. Request content that does not fit its command (bit op on a word device, unknown device code, bad digit, zero points on 3C, wrong data length in F3) is answered with unsupported*, as for 3E/1E.
  5. EOT is counted at the EOT byte; in F4 the following CR LF are skipped as junk. Counted while muted, not consuming a `muteNext`.
  6. Station mismatch: logged with `answered == false` (op/head/count decoded), no response, does not consume a `muteNext`, SUM not judged. Network, PC and self-station are not checked and are echoed.
  7. Order: station, mute, SUM (wrong SUM wins over an unsupported command), execute. A wrong SUM request is not executed.
  8. SUM digits are accepted in lower case; non-hex SUM characters are a wrong SUM. A control code in a SUM position restarts the scan (F1/F2/F4/F3).
  9. `f3ShortResponseHasSum` applies to both F3 short responses (QACK/GG without data and QNAK/NN), as SPEC-core-protocol states; with `sumCheck == false` there is never a SUM.
  10. Corruption on serial: WrongSubheader leaves it unchanged; WrongSumCheck = SUM+1 only when a SUM is there; WrongRoute and WrongBlockNo recompute the SUM so the named field is the only damage; WrongRoute leaves the 3C self-station alone; ExtraByte goes after CR LF. All documented in `mock_plc.h`.
  11. 1C failRange/outOfRange codes are one byte (low byte of failRange `code`); `MockRequestRecord::answeredWith.info` is not filled on serial (no error information on the wire).
  12. 1C layout is chosen from the command letters received (J/Q = 7-char device), not from `cfg.commandSet`; points 00 = 256 on every 1C command; message wait must be one hex digit and is ignored; spaces for leading zeros accepted in device numbers; point limits of spec 4.4 are not enforced (as on 3E/1E).
